Einzbern（アインツベルン）を Claude Code、Codex、DeepSeek Harness に接続するスキルだ。Einzbern はその三つのホストのためのプロジェクト記憶で、作業項目、知識、議事録が、必要になるプロンプトの前にモデルの前へ現れる。Mana は巡る記憶、Orchestrate はそれをいつどこへ流すかの指揮。このスキルはモデルにエンジンのどの機能をいつ呼ぶかを教え、インストールウィザードを同梱する。

## やることは三つ

**Einzbern を入れる。** ホストに「Einzbern をインストールして」と言えば、ウィザードが引き継ぐ。一画面の質問、一度の確認、エンジンのダウンロードと検証、フックの配線。二つのホストを一度に済ませる。

**いつ何をするかをモデルに教える。** ナビゲーション表が一枚。始める前に記憶を取り、終えたら結果を作業項目に書き戻し、決定があれば議事録に、教訓があればカードに書く。表はエンジンが自分のバージョンに合わせて生成するので、モデルが読む動詞はエンジンの動詞と一対一で対応する。

**自分では何も持たない。** データも、ルールも、設定もない。記憶は使用者が親ディレクトリを選ぶ共有総合庫 `Ether` にあり、プロジェクトの識別子で区別する。既存のプロジェクトの `.ether` 庫も引き続き使える。原則と変数は Atelier（アトリエ、魔術師の工房。ここではローカルの管理ページ）にある。このスキルはその表とそのウィザードでしかない。

## インストール

skills コマンドで：

```
npx skills add tpmoonchefryan/mana-orchestrate
```

あるいはホストに言う。Mana Orchestrate というスキルを探して入れて。

置き場所はホストの skills ディレクトリ。Claude Code は `~/.claude/skills`、Codex と DeepSeek Harness は `~/.agents/skills`。DeepSeek Harness では各プロンプト前の想起をプラグイン dsh-mana-orchestrate が担い、フックファイルは書かない。次にプロジェクトのディレクトリで言う。Einzbern をインストールして。

ウィザードが尋ねるのは、新規か既存の庫からの復元か、`Ether` をどこに置くか、そこがクラウド同期フォルダか、言語は何か、AGENTS.md にナビゲーション節を書くか。`Ether` はフォルダ名で、親ディレクトリはローカルディスク、外付けディスク、同期フォルダから使用者が選ぶ。後続のプロジェクトは保存済みの場所を既定で再利用する。最後に書き込む予定のファイルを全部列挙し、あなたが一度だけ確認する。エンジンはこのスキルと同じバージョンのリリースからダウンロードされ、ダイジェストを検証してから配置される。ローカルのアーカイブがあればオフラインでも入る。

その後のことはすべて同じウィザードのモードだ。更新、修復、TCRN Workflow からの移行、アンインストール、健全性チェック。「Einzbern を更新して」と言えばよい。

コミットもプッシュもしない。あなたの .gitignore を書き換えず、何も削除せず、エンジンのダウンロード以外でネットワークに触れない。

## 入れたあと

あなたは普段どおり仕事をする。毎回のプロンプトの前にホストがそれをエンジンに渡して一度検索し、強く関係する見出しがあればコンテキストに入り、なければ何も起きない。モデルはナビゲーション表に従って正しい瞬間に記録する。見たいとき、変えたいときは Atelier を開く。

## 利用量を抑える仕組み

> **Codex 専用ワークフローは提供済みです。** Codex Desktop では、主力層の意思決定と経済層の調整を独立した二つの対話に分けます。他のホストはそれぞれのネイティブ経路を維持します。以下の費用は 2026-10-31 に過去のサンプルから算出したもので、明示した推定条件に基づく比較です。利用枠を一定割合削減できるという約束ではありません。

長時間の作業では、コードを書く以外にも利用量が発生します。派遣、待機後の再開、状態の復元、ログの読み取り、サブエージェントの結果受信でも、モデルが繰り返しコンテキストを処理することがあります。Einzbern と Mana Orchestrate は、役割分担、バッチの境界、読むコンテキストの範囲から、この負担を抑えます。

- **作業に応じてモデルのカテゴリを選ぶ。** 計画、複雑な判断、独立した受け入れ検証は主力カテゴリから始めます。範囲の明確な実行と定型的な調整には、設定された経済カテゴリを使います。実際のモデルと推論強度はホストのポリシーで決まり、特定モデルに固定しません。
- **バッチ全体の目標を実行する。** 分解後は依存関係に沿って分包し、作業エージェントが担当を完了します。受け入れ検証と問題の処置はバッチ末にまとめ、個々の項目ごとに完了、派遣、検証を繰り返す往復を減らします。
- **必要な内容だけを読む。** 問題と証拠はバッチの記録に残します。主対話は判断に必要な結果と証拠の場所を受け取り、大きなファイル、ログ、計画は抜粋で読みます。
- **すべての役割を費用に含める。** 主対話、経済調整対話、作業エージェントを合わせて集計し、失敗、再試行、報告の負担も残します。主対話の利用量が減っても、全工程の利用量と合わせて評価します。

### ホストごとに異なる調整経路を使う

| ホスト | 採用する方式 | 最適化の重点と根拠 |
| :--- | :--- | :--- |
| **Codex Desktop：専用の二対話方式** | 主力の独立した意思決定対話がバッチ全体の目標を渡します。経済層の独立した調整対話が作業サブエージェントを派遣し、待機して結果を受け取り、バッチ末に一度だけ主力へ報告します。 | 過去の実行では、頻繁な調整を長い主力対話に残すと費用への影響が大きくなりました。この作業を経済カテゴリに移し、主力対話の呼び出し頻度を抑えます。 |
| **Claude Code：ネイティブ経路を維持** | 一つの主対話が、ホストのバックグラウンド実行と完了通知を使って作業サブエージェントを調整します。 | ネイティブ通知で結果を受け取れます。モデルカテゴリ、定期的な起動、返す内容、検証の周期を引き続き最適化します。現在のサンプルからは、独立した調整対話を一般的に追加する必要性は示されていません。 |
| **DeepSeek Harness：ネイティブ経路を維持** | 一つの主対話がランタイム管理のサブエージェントを使い、Mana Orchestrate プラグインが記憶の接続とブリッジの重複排除を担います。 | ランタイムが完了通知とリソース回収を担います。過去の記録でも、複数の返却が一つの主対話応答にまとめられる例が確認されています。追加の最適化は実際のモデルと調整費用の割合に応じて評価します。 |

二対話方式は **Codex ワークフローの唯一の方式**であり、従来の収集 hook 経路を置き換えました。他のホストには影響しません。経済調整対話は作業エージェントの結果を直接受け取り、別の収集エージェントは設けません。実装、統合、独立した受け入れ検証は、それぞれの作業エージェントが担当します。主力と経済のモデルカテゴリは必須で、旗艦カテゴリは任意です。

この編成は、モデルがホストの対応ツールを使って実行します。エンジンはバッチと受領記録を保存しますが、自ら対話を作成したり、派遣したり、メッセージを送ったりはしません。

Codex 自体もサブエージェント、待機、結果の集約に対応しています。専用方式は観測された調整費用を対象とします。CC と DSH がネイティブ経路を維持することも、結果返却後のコンテキスト処理がない、あるいは将来も最適化が不要という意味ではありません。ホストの機能は [Codex サブエージェントの文書](https://learn.chatgpt.com/docs/agent-configuration/subagents)、[Claude Code のバックグラウンド・サブエージェントの文書](https://code.claude.com/docs/en/sub-agents#run-subagents-in-foreground-or-background)、[DSH のネイティブ委譲の文書](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/subagent/tool-subagent/README.md)を参照してください。

### Codex の実例：29.3 時間の同じ利用量で三方式を推定

あるデザインシステム開発の記録は、**29.3 時間、81 対話、7,763 件の一意なモデル応答**を含みます。主力の意思決定、経済調整、すべての作業エージェントを集計しています。観測終了時も作業は進行中であり、以下はその時間枠の利用量です。最終検証を通過した成果物全体の納品費用ではありません。

| 作業方式 | Standard 参考 credits | 主力調整方式を 100% とした比率 | データの性質 |
| :--- | ---: | ---: | :--- |
| **主力の意思決定＋経済調整＋カテゴリ別の作業エージェント** | **2,610.58** | **49.3%** | 観測したリクエストと利用量を、各応答で実際に使ったモデルの単価で換算 |
| 主力がすべての調整と待機を担い、作業エージェントは変更しない | 約 5,300.52 | 100% | リクエスト、token、キャッシュ構成を維持し、経済調整を主力モデルの単価で再計算 |
| サブエージェントを使わず、すべて主対話で実行 | 約 5,116.83 | 96.5% | 識別可能な純粋な代理間通信を除き、残す作業を主力モデルの単価で再計算 |

この推定では、二対話方式の費用は主力調整より約 **50.7%**、主力単独実行より約 **49.0%** 低くなります。累計参考費用の **80.5%** は作業エージェント、**10.8%** は主力の意思決定、**8.7%** は経済調整です。

比較用の主力モデルは GPT-6.1 Sol です。実際の記録には GPT-6 Luna と少量の GPT-6.1 Terra も含まれます。これらは事例の測定条件であり、製品が固定するモデルではありません。参考単価は [OpenAI 公式 Pricing](https://learn.chatgpt.com/docs/pricing)を参照しています。

**50.7% は、すべての調整作業を同じ利用量のまま別単価にした差です。** 派遣、待機、復元、結果回収、報告などを含みます。「バッチでの返却だけで token が 50.7% 減った」とは書けません。比較する二方式は実際には再実行しておらず、コンテキストの増加、キャッシュの変化、逐次実行時間、成果物の品質の差は未知です。

### サブエージェントが返却した後、主対話はどれだけのコンテキストを処理するか

派遣と待機のツールだけを数えると、結果受信後の処理が抜けます。そのため、返却イベント後の最初の一意な計量対象応答も集計しました。複数の返却が一応答にまとまる場合は一度だけ数え、ストリーミングの内容ブロックを重複計上しません。返却付近の処理量を示すもので、通知だけが応答全体の費用を発生させた証明ではありません。

| サンプル／役割 | 受信した返却イベント | 最初の受信応答 | 応答あたり平均入力、キャッシュ込み | キャッシュ読み取り比率 |
| :--- | ---: | ---: | ---: | ---: |
| CC：四つの主対話 | 完了通知 212 件 | **207 回** | 約 636k token | 96.5% |
| DSH：公式 Pro の主対話 | 完了通知 112 件＋結果転送 69 件 | **120 回** | 約 395k token | 99.1% |
| Codex：主力の意思決定対話 | バッチ末の報告 12 件 | **12 回** | 約 272k token | 98.2% |
| Codex：経済調整層の全体 | 最終返却 78 件＋代理メッセージ 9 件 | **87 回** | 約 165k token | 97.8% |

DSH の完了通知 112 件だけでは、最初の受信応答は **61 回**です。既存経路でも返却の集約が行われていることを示します。別途転送された結果も応答を発生させ、合計が表の 120 回になります。

Codex の経済層は個々の返却を引き続き受け取り、主力対話はバッチ末の報告を受け取ります。両層のリクエストと費用をすべて含めています。表では作業、継続時間、モデルが異なるため、回数や入力量を直接差し引いてホスト間の削減率を算出することはできません。累計入力にはキャッシュの繰り返し読み取りも含まれます。

### Codex の二対話方式を、当面 CC と DSH に広げない理由

ホストごとの実際の履歴に返却後の処理を加え、選択した作業を経済モデルの単価で再計算すると、追加検証に値する費用の余地を推定できます。CC は **Haiku 5.5**、DSH は公式 **Flash 4.1-1017** を比較対象としました。追加のモデルで作業を再実行してはいません。

| 過去のサンプル | 調整確認＋最初の受信応答を経済単価にした総費用の差 | 返却後の処理区間全体を含む広い推定 |
| :--- | ---: | ---: |
| CC：四つの対話ツリー、Opus 5.5 → Haiku 5.5 | **約 3.8%** | **約 6.6%** |
| DSH：公式 Pro → 公式 Flash | **最大 6.8%** | **最大 11.2%** |
| DSH：公式 Flash の小サンプル → 同単価の Flash | **モデル単価の差は 0%** | **モデル単価の差は 0%** |

広い推定は、返却から最初の新規派遣、現在のターンの終了、または独立したユーザー入力までを含み、読み取り、統合、判断も計上します。これらをすべて経済カテゴリへ移せるか、追加の調整層に伴う起動、引き継ぎ、キャッシュ、品質、保守の費用がどれほどかは実測していません。表の差は達成済みの削減ではありません。

CC の四対話では、それぞれ約 **2.9%、3.0%、2.4%、11.1%** で、3.8% は加重集計です。より新しい DSH の Claude 主対話二サンプルでは、調整と最初の受信処理を Flash 単価にした差が、それぞれ約 **0.7%–1.4%**、**5.3%–7.8%** でした。効果はモデルと作業によって異なり、すべてのプロジェクトに同じ比率は約束できません。

これらのサンプルは、Codex に専用の二対話最適化を採用し、CC と DSH は既存のネイティブ経路を維持しながら、重複通知、避けられる起動、返却内容、キャッシュ効果を引き続き確認する判断を支えます。ネイティブ完了通知は接続機能の根拠です。独立した調整対話を追加するには、追加費用と成果物の品質を含む証拠がなお必要です。

### 待機そのものと、待機後のモデル呼び出しを分けて計量する

待機ツールがブロックしている時間そのものから、新しいモデル入力は生じません。タイムアウト後にモデルを再び呼び出すと、コンテキストを再処理し、出力を生成します。

この Codex 記録全体では、主力が **244 応答、281.14 Standard 参考 credits**、経済調整層が **4,430 応答、226.68 credits** でした。どちらも合計 2,610.58 credits に含まれています。12 回はバッチ末の返却後の最初の応答だけを指し、主力全体の呼び出し回数ではありません。

経済調整層にはなお、**待機タイムアウト後の計量対象応答が 567 回**あり、約 **9,181 万入力 token** を処理しました。その約 **98.9%** はキャッシュ読み取りで、**26.95 参考 credits** に相当します。頻繁な再開を経済モデルに移す費用上の利点を示す一方、タイムアウト後の再開を減らす余地も残ります。空のポーリングをすべて排除したとは言えません。

**サンプル範囲。** Codex の観測期間は中国標準時（UTC+8）2026-10-29 21:28:39 から 2026-10-31 02:46:01 までで、独立した二つのチャットと、そのすべてのネイティブ作業エージェントを含みます。他のプロジェクト、ワークフロー開発、今回の利用量監査は含みません。CC は主対話 4 件、サブエージェントログ 210 件、一意な応答 27,767 件です。DSH は対話ツリー 4 組、115 セッション、4,672 応答で、異なる月とモデル経路を含みます。元の私的な対話ログは公開説明には添付しません。

**時間経過による変化。** Codex の最初の 11.6 時間は 932.03 参考 credits で、同量の主力調整方式に対する推定削減率は 58.5% でした。追加の 17.7 時間は 1,678.55 credits、削減率は 45.1% で、累計は 50.7% です。調整作業だけを同量で比較したモデル単価の差は約 92.2% ですが、全工程の削減率には使えません。

**Codex 三方式の計算。** 主力調整の比較は、観測したリクエスト頻度、token、キャッシュ構成を保ち、経済調整の役割に適用する単価だけを変更します。主力単独の比較では、純粋な代理の派遣、待機、状態照会、通信として識別できる 1,083 応答を除きます。ガバナンス上の読み取り、実装、統合、検証、プロセス待機は残します。確実に分離できない起動時コンテキストの重複は残しています。一つの長い対話でのキャッシュ、逐次実行時間、独立した受け入れ検証の品質差は実測していません。

**返却後の計数。** CC のバックグラウンドコマンド通知とサブエージェント通知は区別し、親メッセージの関係から後続応答を照合できます。他のホストはネイティブイベントの順序で関連付けます。すべてのホストを同一条件で再実行できるほどの完全なリクエスト本文はないため、「返却後の最初の計量対象応答」は、各 token が返却イベントだけで生じたという意味ではありません。CC の調整候補には、別途識別した定期実行、通知、バックグラウンド監視の確認も含めます。DSH は識別可能な代理調整と、完了通知・結果転送後の最初の応答を含めます。同じリクエストは和集合として一度だけ計上します。

**単価の確認日と単位。** 単価は 2026-10-31 に確認しました。Codex は [公式 Standard 参考 credits](https://learn.chatgpt.com/docs/pricing)、Claude は [公式 Global Standard API 単価](https://platform.claude.com/docs/en/about-claude/pricing)、DeepSeek は [現在の公式オフピーク単価](https://api-docs.deepseek.com/quick_start/pricing/)に統一しています。過去のピーク時間や祝日の請求は再現していません。異なるホストの API 単価による参考値と Codex credits は同一通貨として扱えず、実際の請求額やサブスクリプションの週次利用枠とも一致しません。

**キャッシュと欠落データ。** [Haiku 5.5 の公式料金](https://platform.claude.com/docs/en/models/haiku-5-5/overview)では、一リクエストの完全な入力が 100k token を超えると高い単価を使い、閾値にはキャッシュの読み書きも含めます。今回はリクエストごとに区分しました。DSH Pro ツリーの Qwen 応答 7 件は単価が不明で、ゼロとは仮定していません。そのためツリー全体の比率は上限だけを示します。DSH の Claude にはキャッシュ書き込みの保持時間が不明なものがあり、5 分と 1 時間の単価で幅を残しています。第三者経由の実際の料金は未検証です。推論は出力に含まれるため、二重には計上しません。
