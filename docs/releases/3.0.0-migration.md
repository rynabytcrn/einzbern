# 3.0.0 migration and release preparation

Status: source preparation, not a published release, formal release admission or
authorization to install on a device. The public baseline is 2.2.1. The repository's
2.2.3 identity was an unpublished candidate. The next version is major because the
public configuration-write behavior is intentionally incompatible.

## Preserve the new authority, document the break

An old valid `settings-set models.escalation.enabled=false` project write no longer
succeeds: the new engine refuses it with `SETTINGS_KEY_DEVICE_LEVEL`. The same
boundary covers new `models.*` and `quota.*` project writes. Historical records are
still readable, but are not execution-policy authority.

Use the device-host policy entry point for the explicitly selected host. Review the
actual categories, ordered runner/model/effort combinations, escalation and any quota
thresholds before changing it. The existing governed write requires a valid Owner
decision naming `models.engine-policy`; this is a configuration-change boundary,
not a requirement for a new decision every time an unchanged policy is used.
Do not copy fixture decisions or silently translate historical project settings
into a new device policy. Do not create another host's policy by copying Codex.

New shared path declarations must use portable relative values or declared local
bindings. Resolve each device's bindings independently. Private variable export
and generated projection refresh remain explicit. No migration step rewrites old
events, exports private values automatically or changes the host application's
own default model.

## Routine dispatch must not become an Owner form

Admission is a machine decision, not an interactive approval dialog. Mechanical
request fields, canonical digests and evidence associations belong to the invoking
software, not to the Owner. Valid existing permissions are not a reason to ask for
the same approval on every dispatch. Separate changes to policy, installation,
credentials, write scope and publication still need their applicable authority.

The baseline source contains an admission resolver and a caller-evidence validator,
not an installed native dispatcher or account reader. A generated Skill instruction
alone does not supply those integrations. The current recall/navigation hooks do
not intercept native dispatch or collect its completion result. Historical retired
controller/observer modules are not a supported workaround.

Capability evidence must come from the actual invoking host; the desired policy
tuple is not evidence that the host supports it. When quota is configured, both
required windows must have fresh observations under the existing five-minute
contract. Unknown values are not zero, and a successful model probe is not an
account-usage observation. Unsupported collection must be reported as a concrete
capability gap, not a recurring request for the Owner to compose JSON or guess
account numbers.

The process-evidence contract needs actual stdout, stderr and exit code, or an
explicit unavailable observation. A native tool returning only task status/text
does not thereby provide process streams or exit zero. Supporting a different
transport requires its verified result contract; do not relabel test output or
an invented envelope as a native response. Association is not authentication, and
complete association is not the same as successful execution.

The installed `execution-prepare` and `execution-record` commands remove duplicate
binding work and retain private create-new records, including refused preparations,
failed exits and unavailable observations. They consume machine-produced inputs;
they do not by themselves complete native collection or dispatch. Keep the
supported transport and remaining integration evidence explicit in the candidate
acceptance report. No unattended end-to-end native claim is made by this document.

This is an integration boundary, not a claim that the hosts have no relevant APIs.
For example, the current [Codex App Server documentation](https://developers.openai.com/codex/app-server)
describes model/effort discovery, account rate-limit windows and terminal turn
notifications. A future adapter must bind the actual installed interface and
invocation: quota windows have explicit durations and may be absent, so `primary`
must not be assumed to mean five hours or `secondary` one week. A completed turn
is not a process exit code. These published APIs do not establish that this engine
has implemented or verified such an adapter, and do not authorize starting one on
the Owner's device.

## Installation, recovery and helper lockstep

Before a real upgrade, identify the intended device, host and library, verify the
exact final archive and retain a verified backup and rollback route. Exercise a
disposable target first. A rollback selects the old installation; it does not undo
new library history or prove that an old engine understands new declarations.
Review all planned live writes separately before applying them.

Regenerate Mana Orchestrate from the final engine. A helper that can bootstrap a
new archive is not necessarily carrying the new workflow instructions. Keep both
public versions equal. Preserve the tracked helper archive script with
`--keep-extra skill/mana-orchestrate/scripts/create-skill-archive.mjs`; do not hand-edit
generated helper files or remove this extra as incidental cleanup.

## Formal release remains a separate, bound operation

Follow [the release policy](../versioning/release-policy.md). Finish source changes
before `generate`; the prescribed release-only commit cannot contain new runtime
implementation. `generate` requires an existing registered release project covering
both exact repository roots and nonempty enabled required gate declarations.
An empty declaration list cannot be replaced by a green GitHub page or a synthetic
fixture receipt. A renderer preview is not `generate`/`finish` admission.

The final release candidate must bind its source and version, both repository
commits, helper output, archive SHA-256, selected gates and recorded results.
Regenerate release notes, CLI documentation and Wiki inputs at the batch end.
Existing 2.2.3 receipts remain evidence of their original identities, not 3.0.0.
Do not overwrite an existing version/tag or weaken a refusal to complete preparation.
Tagging, publishing, Wiki/About changes and live deployment are separate actions;
this document performs none of them.

Private PF3/U18 inputs, original-method PF2/PF3 reconciliation, real Mac/host and
two-device synchronization remain explicitly scoped in
[native acceptance](../implementation/native-acceptance.md). They must not be
claimed complete from Linux fixtures, nor automatically expanded into unrelated
tests or previously excluded probes.
