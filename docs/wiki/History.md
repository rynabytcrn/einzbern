## Home

### TCRN Workflow 文档

面向 AI 代理交付的治理框架。它声称的每一项能力，都是一条能被机器证伪的判据。

仓库首页只讲这是什么、给谁用、怎么装。这里讲怎么用、它由什么构成、以及它在哪里停止。

#### 三件需要先知道的事

- **能力清单以 `commands` 的输出为准，不以任何文档为准。** 文档可能落后于代码，命令目录不会。
- **门的绿红不是建议。** 判据的覆盖范围改了却没重新证明，构建会失败。
- **推送、打标签、发版是各自独立的关卡。** 本地测试全绿不等于可以发出去。

## 信任链与发版

旧文档把 `tcrn-workflow-helper` 描述为一个单文件、零依赖的引导器，并记录了对引导器摘要进行人工核对、之后按密码学约束接受发行字节的模型。旧版受理身份由仓库地址、版本、提交、树对象和带注解标签对象共同绑定；不匹配的归档会以 `IDENTITY_MISMATCH` 失败关闭。

旧说明把发版列为独立关卡：本地测试通过不自动授权推送、打标签、部署、发版、对外发布或第三方账号声明。它还将可复现归档、SBOM、来源证明、校验和和发布说明列为当时的发行组成。

| 当时列出的保证 | 当时描述的做法 |
| --- | --- |
| 可复现产物 | 干净克隆的 CI 从零重建技能归档、源码归档、SBOM，并核对摘要 |
| 敌意归档防护 | 解包前拒绝路径穿越、绝对路径、控制字符、非 NFC、冲突路径、链接、特殊文件和摘要篡改 |
| 不碰活动目录 | 安装类操作只在一次性测试根目录运行，活动目录在探测前被拒绝 |
| 事务化生命周期 | 改动先暂存并记录；崩溃恢复由进程终止注入证明 |

旧稿记录的受理版本为 Workflow `1.0.1`、helper `1.0.1`，并指向仓库的 `CHANGELOG.md`。这些版本号是历史快照。

## 判据与门

旧文档区分三层：`verification-map.yaml` 中的判据、`pnpm verify:p1` 的 P1 门，以及工作完成时使用的验收门组。它当时记录 122 条判据、24 道 P1 门和九组验收门。

旧稿按框架卫生、惰性证明和运行时能力分类判据，并说明每条判据包含命令、预期原因码、fixture 路径与摘要，以及一条经实测的红腿。fixture 摘要变化会使 `VERIFICATION_MAP_DIGEST_MISMATCH` 失败。

当时的 P1 序列如下；清单只作历史记录：

```text
format-check  lint  typecheck  build  test  portal  test-trust
archive  sbom  licenses  vulnerabilities  source
no-sibling-dependency  lifecycle  offline  governance
workspace  privacy  roots  ci  verification-map  history  budget  links
```

旧稿把门的包含关系描述为机器可读策略，并特别提醒 `guard-check` 会修改工作树，应独占运行。

## 命令参考

旧命令参考说明，`commands` 的输出才是权威清单：它列出动词、标志、标志取值类型、写入属性和可用性。它当时记录 137 个动词，其中 65 个写入、72 个只读，并按工作记录、知识、会议、适配器、画像、迁移、产物、设置、项目、模型计划、交换和租约等用途分类。

旧稿列出的使用纪律包括：写入前读取版本并立即以 `--expected-version` 写入；遵守 `planned → ready → active → done` 状态图；对大链使用分页读，避免超过 1 MiB 限制的整体 `export`。

## 已知限制

旧限制页记录了以下设计边界：

- 一个工作区由一个写者串行写入；并行工作使用多个工作区。
- 工作区链在数千条事件量级开始变慢，整体 `export` 的规范形式超过 1 MiB 会以 `INPUT_OVERSIZED` 拒绝。
- 备份可以放在别处，但恢复只支持原路径；知识库和产物库与事件链高水位绑定，不能单独恢复。
- Git 可作为完整性见证，但不能重建存储所需的空目录；存储文件不能在工作区之间复制。
- 旧迁移页描述的 relocation 动词族有 16 条上限，并指出它表达授权而非身份认证。
- 引擎不保护产品源码树、产品供应链或业务代码正确性，也不认证行动者身份或墙钟时间。

原页给出事件规模与运行时间样本；这些具体数字依赖当时的机器、链和实现，不能外推为当前承诺。

## 常见问答

旧 FAQ 将框架和普通任务跟踪器区分为：前者维护可执行的能力判据，并在判据失效时让构建失败。它把文件格式和哈希链列为当时不使用数据库的原因，同时指出规模上限是代价。

旧稿中的“零运行时依赖”指框架自身的依赖字段为空，并不代表被管理项目也没有依赖。它还说明网络守卫只覆盖指定的验证进程，不覆盖代理的 shell 或被管理项目的构建。

FAQ 回答了部分使用、状态跳转、门运行时间、命令文档与目录不一致、阶段计时证据过期、以及发布是否自动等问题。其核心提示是以 `commands` 为准；推送、打标签、部署和发布仍需各自授权。

## 快速开始

旧快速开始页记载固定工具版本 Node `24.16.0`、pnpm `11.3.0`，并建议离线、冻结锁文件地安装依赖，运行 `verify:p1`，然后构建和列出命令。

它用 `validate`、`status` 和 `work-create` 展示创建工作区及 Story 的步骤，强调写入必须带刚读取到的版本号。检索示例使用 `work-list`；大链避免整体 `export`。常见错误说明包括状态跳转被拒、CAS 版本过期，以及读错引擎副本导致重放失败。

## 架构总览

旧架构页将系统分为冻结的 V1 协议、文件原生引擎、能力层、宿主适配器和可复现发行层。它强调协议只增不改，扩展独立注册；事件链按 `priorHash`、`payloadHash` 和 `eventHash` 相扣，写入使用 `--expected-version`。

当时的存储说明提到 NDJSON 事件分段、分段与标签等索引、快照加尾部重放，并将这些实现参数描述为可配置项。宿主适配器默认惰性，安装本身不等于激活。
