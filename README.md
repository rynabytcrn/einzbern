## 周三下午发生的事

周一，你在 Claude Code 里定了一件事：登录页的按钮改用设计系统的新组件，旧样式保留到 1.4。

周三，你在 Codex 里说「注册页也顺手改了」。它动手之前，上下文里已经有三行：周一那张 Story 和它的验收标准，那条「旧样式保留到 1.4」的决定，还有上周留下的一张卡片：这个组件在 Safari 下要补一个属性。

你没有粘贴任何东西，也没有提醒它去查。这就是 Einzbern 做的全部事情：记下来，在对的时候拿出来。

## 一台愿望机

圣杯是愿望机：许愿，得到结果。愿望机都有一个特点，愿望说得不具体，实现出来的很可能不是你要的。

Einzbern 照这个来。它只强制两件事：一张工单要写清目标，要写清怎样算完成。其余怎么写、怎么拆、怎么做，模型按自己的思路来，它不插手。

工单、知识、纪要、变量，是在这台机器里流转的魔力。它们保存在用户所选位置的共享总库 `Ether` 里，多个项目在库内区分。以太，魔力在现实中固定下来的介质。模型在每条 prompt 前从那里取，做完事往那里存。

## 它记什么

**愿：工单。** Initiative、Epic、Story、Subtask 四级。Story 是最小的完整意图，只索引它。工单之间的关系是字段：谁阻塞谁、谁实现谁、谁取代谁、由哪份纪要决定。不用另写一段话去解释。

> Story：登录页按钮改用 DS 组件。验收：默认、悬停、禁用三种状态与 Storybook 一致。

**决定：纪要。** 你的决定，和模型做的技术决定。每条决定有编号，工单与卡片用编号引用它。不要求模型开会讨论，只要求记下来。

> 纪要 D3：旧按钮样式保留到 1.4，1.5 移除。

**坑：知识。** 一张卡片记一条环境事实或教训，是没有任何工单或纪要以字段承载的那种东西。模型自己判断什么值得记，写入即可检索。旧卡只在被新卡冲突时退役。时间不是理由，容量也不是。

> 卡片：DS 按钮组件在 Safari 下要加 appearance: none，否则圆角丢失。

**变量。** 分宿主的模型档位表、项目的设计系统地址、你自己定义的键值。它们渲染进 AGENTS.md。你在 AGENTS.md 里写「实施用主力档」，Claude Code 与 Codex 各自换算成自己的模型。

## 它怎么出现在模型面前

每条 prompt 发出前，宿主把它交给引擎检索一次。有强相关的，就把标题送进上下文：

```
[Story 已完成] 登录页按钮改用 DS 组件 · 验收：三种状态与 Storybook 一致
[纪要 D3] 旧按钮样式保留到 1.4，1.5 移除
[卡片] DS 按钮在 Safari 需要 appearance: none
```

没有强相关的，就什么都不做。模型要正文时自己取。做完一件事，模型把结果记回工单，有决定记纪要，有教训写卡片。

## 什么时候你会想要它

- 任务跨了三天五个会话，第四天的模型还知道第一天定了什么。
- Claude Code、Codex 和 DeepSeek Harness 换着用，几边读同一份记忆。
- 夜里跑无人值守的批量实施，早上能追溯每一步做了什么、依据哪条决定。
- 桌面机在跑，你带着笔记本出门接着写。

目前面向单人多设备。多人共用一份记忆没有做。

## 为什么是它，而不是一个记忆插件

市面上的记忆方案大多是一个向量库或一叠笔记：把对话片段存起来，按相似度捞回来。它们记的是「说过什么」，Einzbern 记的是「决定了什么、要做什么、学到了什么」，三种记录各有结构，彼此用编号引用。

| 你需要的 | 记忆插件 | Einzbern |
|---|---|---|
| 一条决定和它的来龙去脉 | 一段相似的聊天记录 | 有编号的纪要，工单和卡片用编号指向它 |
| 一件事做到哪了 | 无 | 工单四级，关系是字段：谁阻塞谁、谁取代谁、由哪份纪要决定 |
| 换宿主 | 各记各的 | Claude Code、Codex 与 DeepSeek Harness 读同一个 Ether |
| 换设备 | 手动同步或不同步 | 放进云文件夹，每台设备一条流，同时写不冲突 |
| 想看、想改 | 翻文件 | Atelier：变量、规则、门配置、库状态一页管理，改了立刻渲染进 AGENTS.md |
| 模型的做事方式 | 插件不管 | 不管束；七条原则默认关闭，按项目自选 |
| 记录能不能被篡改 | 能 | 只追加的哈希链，改一条后面全对不上 |

变量是它区别于插件的另一半：分宿主的模型档位表、设计系统地址、你自己的键值，都在 Atelier 里改，渲染进 AGENTS.md，同一份规则文本在两个宿主上各自换算。

## 安装

Einzbern 由一个 skill 带进来：Mana Orchestrate。Mana 是流转的记忆，Orchestrate 是指挥它何时流向哪里。它教模型什么时候该调引擎的哪个功能，也带着安装向导。

用 skills 命令装：

```
npx skills add tpmoonchefryan/mana-orchestrate
```

或者对宿主说：找一个叫 Mana Orchestrate 的 skill，装上。

然后在项目目录里说：安装 Einzbern。向导问一屏问题：全新安装还是从已有的 `Ether` 恢复，生成物放哪，是否在云同步文件夹里，用什么语言，要不要在 AGENTS.md 写导航段。最后列出将写入的文件，你确认一次。更新、修复、从旧版迁移、卸载、体检，都是同一个向导的模式。

它不提交、不推送、不改你的 .gitignore、不删任何东西，除下载引擎外不联网。

## 日常怎么用

你正常工作，记忆自己出现。

想看或想改的时候，打开 Atelier。魔术师的工房，在这里是本机的一个网页：哪些原则启用了，变量是什么，门怎么配，记忆库现在什么状态。不常驻，用时打开。

AGENTS.md 是你的。Einzbern 只写带标记的段落：你启用的原则，和要渲染给模型的变量。段落被你改过，它就不再覆盖，怎么处理由你在 Atelier 里选。

内置原则一共七条，叫 Command Spell。令咒，对从者绝对有效的命令。它们不是强制的：默认全部关闭，你在 Atelier 里按项目自选启用，不启用也不影响记忆本身。

- 自主运行：不在任务中途问「要不要继续」，可逆的动作直接做，只有破坏性动作与范围变更才停。
- 批量处理：一次拆分产出的工单是一批，见红只记不修，批末一次处置，一批一次汇报。
- 无人值守指令：不用会弹确认框的写法，删除改为移动，命令里不 cd，只写工作目录。
- 静默汇报：工作进行期间不输出汇报，只在全部完成或全部阻塞时汇报。
- 设计权威与一致性：先读项目的设计权威与已发布的组件规范，组件和视觉改动先改权威、发布后再接入，同类组件保持一致。
- 无效残余收尾：谁建的临时目录、副本、工作树和后台进程谁负责，批次结束（包括失败）就按用途清掉，证据与可重建的副本分开。
- 目标书写契约：goal 只写可验证的终态，不写授权，每条都带「阻塞于只有你能做的决定」的出口。

## 多设备与云文件夹

`Ether` 是共享总库的文件夹名称，父目录由用户选择，可以放在本地磁盘、外接磁盘或 OneDrive、iCloud 等同步文件夹中。多个项目在同一个库内按项目身份区分，后续项目默认复用首次选择的位置。事件记录在 `akasha/<设备id>/`；缓存、写锁与备份在 `Ether/.einzbern/<设备id>/`，每台设备分别使用自己的目录。设备身份、注册表、宿主配置与已安装引擎仍留在本机 `~/.einzbern/`。旧版 `.ether` 库保持兼容。

## 我们自己怎么用它

这是 Einzbern 自己的开发方式，也是我们建议的用法。你可以只用其中一层。

**两条对话。** 一条是设计对话，用旗舰档，和你讨论方向，把决定记成纪要，把要做的事拆成 Initiative、Epic、Story，写进 Ether。另一条是实施对话，用主力档，从 Ether 读 Story，不写代码，只派工、落链、跑门、汇报。

**一批做完。** 实施对话派一个经济档子代理把整个 Initiative 的 Story 一次拆成 Subtask，每张写明改动文件与依赖。然后按依赖与文件重叠分包：有关联的进同一包按序做，无关的各成一包。每包一个经济档子代理，在自己的 git worktree 上并行做，包完成即退役。全部完成后一个集成子代理按依赖合并，批末跑一次门、做一次验收，缺陷成批返工。

**当时的四条原则都开着。** 自主运行：可逆动作直接做。批量处理：见红只记不修，批末一次处置。无人值守指令：不用会弹确认框的写法。静默汇报：只在全部完成或全部阻塞时汇报。

**你只在两个时刻出现。** 设计对话里做决定；实施对话收口时看一份汇报，里面待你决定的事项一次列全并附建议。

### 订阅与模型档位（截至 2026-09-26）

建议的订阅：Claude Max 5x 或 ChatGPT Pro 5x。并行子代理的上限按订阅定，超过建议值周限额掉得太快；上限在 Atelier 的 execution.maxConcurrentSubagents 里改。

| 订阅 | 并行子代理上限 |
|---|---|
| Claude Pro 或 ChatGPT Plus | 1 或 2 |
| Claude Max 5x 或 ChatGPT Pro 5x | 3 |
| 20x 档 | 8 或更高 |

并行也不是越多越好，额度快见底时要自动收缩。四个系统变量决定何时收缩，都在 Atelier 里改：

| 变量 | 默认 | 含义 |
|---|---|---|
| quota.fiveHourParallelOffPercent | 75 | 5 小时额度用到这个百分比，并行子代理上限降为 1 |
| quota.fiveHourWaitPercent | 90 | 5 小时额度用到这个百分比，不再派子代理，等窗口重置 |
| quota.weeklyParallelOffPercent | 95 | 周额度用到这个百分比，并行子代理上限降为 1 |
| quota.weeklyWaitPercent | 未设置 | 周额度不设等待阈值，设了才生效 |

下面保留一组模型配置示例，不是默认值或工作流绑定。实际模型与推理强度以你在 Atelier 中维护的 models.tiers 为准。

| 宿主 | 旗舰档 | 主力档 | 经济档 |
|---|---|---|---|
| Claude Code | claude-fable-5-1，max，只用于设计对话，不派工 | claude-opus-5-5，max，子代理编排与验收 | claude-opus-5-5，low，拆分与分包实施 |
| Codex | gpt-6-astra，max | gpt-6-sol，max | gpt-6-luna，max |

## 我们如何节省你的用量

> **Codex 专属工作流已提供。** Codex Desktop 使用独立的主力决策对话与经济协调对话，其他宿主保留各自的原生路径。下文费用数据来自 2026-10-31 的历史样本核算，属于估算条件下的对比，不是固定额度承诺。

长期任务的消耗不只来自写代码。派工、等待后的接续、恢复状态、读取日志和接收子代理结果，也会让模型反复处理上下文。Einzbern 与 Mana Orchestrate 从任务分工、批次边界和上下文范围三个方面控制这些开销。

- **按任务选择模型类别。** 规划、复杂判断和独立验收从主力类别开始；范围明确的执行与例行协调使用配置中的经济类别。实际模型与推理强度由宿主策略决定，不固定绑定某款模型。
- **按整批目标执行。** 拆分后按依赖分包，工作代理完成各自任务，批末统一验收和处置问题，减少逐条完成、逐条派工、逐条验收带来的重复往返。
- **只读需要的内容。** 问题与证据留在本批记录中，主对话接收决策所需的结果和证据位置；大文件、日志与计划按摘录读取。
- **把所有角色计入成本。** 主对话、经济协调对话和工作代理一并统计，保留失败、重试和回传开销。主对话用量下降，需要结合全流程用量判断。

### 针对不同宿主，采用不同的协调方式

| 宿主 | 采用的方式 | 优化重点与依据 |
| :--- | :--- | :--- |
| **Codex Desktop：专属双对话方案** | 主力独立决策对话交出整批目标，经济独立协调对话派出工作子代理、等待并接收结果，批末一次回报主力。 | 历史实践中，频繁协调留在主力长对话内会有明显的费用影响。将这部分工作交给经济类别，控制主力对话的调用频率。 |
| **Claude Code：保留原生路径** | 单主对话协调工作子代理，使用宿主的后台执行与完成通知。 | 原生通知可以接回结果，继续优化模型类别、定时唤醒、回传内容和验收节奏。当前样本未证明需要普遍增加独立协调对话。 |
| **DeepSeek Harness：保留原生路径** | 单主对话使用运行时管理的子代理；Mana Orchestrate 插件负责记忆接入与桥接去重。 | 运行时负责完成通知与资源回收，历史记录也已观察到多条返回合并进入一次主对话响应。按实际模型和协调比例评估进一步优化。 |

双对话形式是 **Codex 工作流的唯一方案**，已替换原有收集 hook 路线，不影响其他宿主。经济协调对话直接接收工作代理结果，不另设收集代理；实施、集成和独立验收由对应工作代理承担。主力与经济是必需模型类别，旗舰类别可选。

这套编排由模型通过宿主支持的工具执行；引擎记录批次与回执，不会自行创建对话、派工或发送消息。

Codex 本身也支持子代理、等待和结果汇总。专属方案针对已经观察到的协调费用；CC、DSH 保留原生路径，也不意味着它们没有上下文回调或永远不需要优化。各宿主能力参见 [Codex 子代理文档](https://learn.chatgpt.com/docs/agent-configuration/subagents)、[Claude Code 后台子代理文档](https://code.claude.com/docs/en/sub-agents#run-subagents-in-foreground-or-background)与 [DSH 原生委派文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/subagent/tool-subagent/README.md)。

### Codex 实践：29.3 小时，三种方式的同量估算

一次设计系统开发记录覆盖 **29.3 小时、81 个对话、7,763 条唯一模型响应**，包括主力决策、经济协调和全部工作代理。任务在采样截止时仍在进行，以下为时间窗口内的用量，不是最终验收通过的完整交付成本。

| 工作方式 | Standard 参考 credits | 以主力协调方案为 100% | 数据性质 |
| :--- | ---: | ---: | :--- |
| **主力决策＋经济协调＋按类别派工作代理** | **2,610.58** | **49.3%** | 观测请求及用量，按各响应实际模型费率折算 |
| 主力承担全部协调与等待，工作代理保持不变 | 约 5,300.52 | 100% | 请求、token 和缓存组成不变，将经济协调改按主力模型计价 |
| 无子代理，全部工作由主力主对话完成 | 约 5,116.83 | 96.5% | 扣除可识别的纯代理通信，再把保留工作改按主力模型计价 |

这组估算中，双对话方式相对主力承担协调约低 **50.7%**，相对主力独做约低 **49.0%**。累计参考费用中，工作代理占 **80.5%**，主力决策占 **10.8%**，经济协调占 **8.7%**。

对照中的主力模型为 GPT-6.1 Sol，实际记录还包含 GPT-6 Luna 与少量 GPT-6.1 Terra。这些名称属于案例的测量条件，不是产品的固定模型绑定。参考费率见 [OpenAI 官方 Pricing](https://learn.chatgpt.com/docs/pricing)。

**50.7% 是全部协调工作同量改价的差异。** 它覆盖派工、等待、恢复、回收和报告等职责，不能写成“批量返回单独减少了 50.7% 的 token”。两种对照方式均未实际重跑，上下文增长、缓存变化、串行耗时和交付质量的差异仍未知。

### 子代理返回后，主对话还要处理多少上下文？

只统计派工和等待工具，会漏掉接收结果后的处理。我们补计了返回事件之后的第一条唯一计量响应；多条返回合并进入一次响应时只计一次，流式内容块不重复计数。它显示返回附近的处理用量，不能证明整条响应的费用都由通知单独造成。

| 样本／角色 | 收到的返回事件 | 首次接收响应 | 每次平均输入，含缓存 | 缓存读取占比 |
| :--- | ---: | ---: | ---: | ---: |
| CC：四个主对话 | 212 条完成通知 | **207 次** | 约 63.6 万 token | 96.5% |
| DSH：官方 Pro 主对话 | 112 条完成通知＋69 条结果转送 | **120 次** | 约 39.5 万 token | 99.1% |
| Codex：主力决策对话 | 12 条批末回报 | **12 次** | 约 27.2 万 token | 98.2% |
| Codex：全部经济协调层 | 78 条最终返回＋9 条代理消息 | **87 次** | 约 16.5 万 token | 97.8% |

DSH 的 112 条完成通知单独对应 **61 次**首次接收响应，说明现有路径已经存在合并返回；另行转送的结果也会引起响应，合计为表中的 120 次。

Codex 的经济层仍接收逐个返回，主力对话接收批末报告。这两层的请求和费用全部计入。表中的任务、持续时间与模型不同，不能用次数或输入量直接相减，推算跨宿主的节省比例；输入累计也包含重复读取的缓存。

### 为什么暂不把 Codex 的双对话形式推广给 CC 和 DSH？

按各宿主的实际历史用量补计返回处理，再以经济模型费率重算，可以估计值得进一步验证的费用空间。CC 以 **Haiku 5.5** 为对照，DSH 以官方 **Flash 4.1-1017** 为对照；未启动额外模型重跑任务。

| 历史样本 | 协调检查＋首次接收响应改按经济模型计价的总费用差异 | 加入返回后整段处理的较宽估算 |
| :--- | ---: | ---: |
| CC：四个会话树，Opus 5.5 → Haiku 5.5 | **约 3.8%** | **约 6.6%** |
| DSH：官方 Pro → 官方 Flash | **不超过 6.8%** | **不超过 11.2%** |
| DSH：官方 Flash 小样本 → 同价 Flash | **0% 的模型单价差** | **0% 的模型单价差** |

较宽估算从返回事件开始，计算到首次新派工、当前回合结束或独立用户输入，其中包含读取、集成和判断。这些工作能否全部下沉到经济类别，以及新增协调层的启动、交接、缓存、质量和维护成本，都未经实测；表中差异不是已实现节省。

CC 的四个会话分别约为 **2.9%、3.0%、2.4%、11.1%**，3.8% 是加权总计。较新的两组 DSH Claude 主对话样本，按 Flash 重算的协调与首次接收处理差异分别约为 **0.7%–1.4%**、**5.3%–7.8%**。收益取决于具体模型与任务，不能为所有项目承诺同一比例。

这些样本支持Codex 采用专属双对话优化，CC 与 DSH 保留现有原生路径，并继续检查重复通知、可避免的唤醒、回传内容及缓存效果。原生完成通知是接入能力依据；是否增加独立协调对话，还需要覆盖新增开销与交付质量的证据。

### 等待本身与等待后的模型调用，分别计量

等待工具阻塞的时间本身不产生新的模型输入。超时后继续调用模型，就会再次处理上下文并产生输出。

这次 Codex 记录中，主力全程 **244 次响应、281.14 Standard 参考 credits**，经济协调层全程 **4,430 次响应、226.68 credits**，都已包含在 2,610.58 credits 的总计中。12 次只指批末返回后的首次响应，不代表主力全程只调用 12 次。

经济协调层仍有 **567 次等待超时后的计量响应**，累计处理约 **9,181 万输入 token**，其中缓存读取约 **98.9%**，折算 **26.95 参考 credits**。本次实践体现了把频繁接续移到经济模型的费用优势，也显示减少超时接续仍有改进空间，不能宣称已经消除全部空轮询。

### 预设规则怎么帮你把 token 花在刀刃上

当时的四条原则不只是纪律，每一条都堵着一处实测过的浪费。数字来自 Einzbern 自己的开发记录，2026-09-26，同一批工作、同一模型。

| 浪费在哪 | 实测 | 哪条规则堵它 |
|---|---|---|
| 一个子代理连续跑，上下文越滚越大，每回合重读一遍 | 一个子代理做 30 张 Subtask：平均上下文 526k，3,740 回合，221M 加权 token，每张 7.4M | 批量处理：分包并行，每包一个新子代理，做完即退役。分包新子代理每张 2.9M，只有它的 39% |
| 中途见红就修，修完再红，门一遍遍重跑 | 前一版里 9 张缺陷单围着一条预算门转，同一个钩子缺陷分四次提交 | 批量处理：见红只记不修，批末一次处置，同一根因算一条 |
| 派一波正撞上额度窗口末尾，全部作废 | 8 个并行子代理在 12 分钟内打满 5 小时额度，零提交，约 15M 白花 | 额度门控：派前读额度，75% 降并行，90% 等重置 |
| 弹出确认框，会话无限等人 | 一次等了 2 小时 12 分 | 无人值守指令：不用会弹框的写法 |
| 主对话每派一次就写一段汇报 | 每段几千 token，都留在主对话上下文里，之后每回合重读 | 静默汇报：只在全部完成或全部阻塞时汇报 |
| 中途问「要不要继续」，等人回答 | 无人在场时一等就是整夜 | 自主运行：可逆动作直接做 |

在上述 2026-09-26 样本的加权成本口径中，缓存读取约占八九成，启动时注入的系统提示与规则约为 52k，占单个子代理成本不到 1%。这些比例只适用于该历史样本，不能推广到其他模型、当前用量或订阅额度。按包提供摘录、命令输出落盘后只取必要部分、大文件按段读取和合并相邻命令，都是该批次采用的上下文控制方式。

并行、代理数量与上下文边界都可能改变总消耗。这个案例支持按包控制上下文和往返次数；新上下文或更高并发本身不构成节省证明，仍需核对全流程费用与交付质量。

## 为什么这样设计

**只提供记忆，不管束方法。** 前一版试过用门、证明和 Stop 钩子把模型框住，一百多个动词、十六道门。我们自己用了两个月：成本远高于收益，模型该忘的照样忘。这一版把它们去掉，留下记录与检索。

**钩子只有一条。** 模型不知道自己不知道什么，检索必须由宿主在每条 prompt 前触发，不能等模型想起来。但钩子里没有任何规则。取什么、给多少，引擎决定。

**AGENTS.md 是你的文件。** 规则要在两个宿主上同时生效，只能写在两个宿主都读的地方。所以 Einzbern 会写进去，但只写带标记的段，只写你启用的东西，改过就不碰。

**只索引 Story。** Initiative 与 Epic 太粗，Subtask 太碎。要知道的事，从 Story 就能知道。

**记录只追加。** 所有派生态都能从记录重建。索引可以只在本机、多台设备可以合并，都是因为这一条。

**配置分两层。** 项目级配置随记录同步，设备级配置留在本机。新装一台设备，重设的是设备，不是项目。
