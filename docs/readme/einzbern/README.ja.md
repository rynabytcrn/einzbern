## 水曜の午後に起きたこと

月曜、あなたは Claude Code で一つ決めた。ログイン画面のボタンをデザインシステムの新コンポーネントに切り替え、旧スタイルは 1.4 まで残す。

水曜、あなたは Codex に「ついでに登録画面もやって」と言う。手を付ける前に、コンテキストにはもう三行が入っている。月曜のあの Story と受け入れ基準、「旧スタイルは 1.4 まで残す」という決定、そして先週残したカード：このコンポーネントは Safari では属性を一つ足す必要がある。

あなたは何も貼り付けていないし、調べるよう促してもいない。Einzbern がやることはこれで全部だ。書き留めて、必要なときに取り出す。

## 願望機

聖杯は願望機だ。願えば、結果が返る。願望機には共通の性質がある。願いが具体的でなければ、叶ったものはあなたの望みと違う可能性が高い。

Einzbern はこれに倣う。強制するのは二つだけ。作業項目には目標を書くこと、何をもって完了とするかを書くこと。どう書くか、どう分けるか、どう進めるかはモデルが自分の考えで決める。Einzbern は口を出さない。

作業項目、知識、議事録、変数は、この機械の中を巡る魔力（マナ）だ。それらはユーザーが選んだ場所の共有ライブラリ `Ether` に固定される。エーテル、魔力が現実世界で形を保つための媒質。モデルは毎回のプロンプトの前にそこから取り出し、仕事を終えたらそこへ戻す。

## 何を覚えるか

**願い：作業項目。** Initiative、Epic、Story、Subtask の四階層。Story は最小の完全な意図で、索引するのは Story だけ。作業項目同士の関係はフィールドであって、文章ではない。何が何を塞ぐか、何が何を実現するか、何が何に取って代わるか、どの議事録が決めたか。

> Story：ログインボタンを DS コンポーネントに切り替える。受け入れ：通常・ホバー・無効の三状態が Storybook と一致。

**決定：議事録。** あなたの決定と、モデルが下した技術的な決定。決定には番号が付き、作業項目とカードは番号で参照する。モデルに会議を求めない。書き留めることだけを求める。

> 議事録 D3：旧ボタンスタイルは 1.4 まで残し、1.5 で削除。

**落とし穴：知識。** カード一枚に環境の事実か教訓を一つ。作業項目にも議事録にもフィールドとして載らない類のもの。何を残す価値があるかはモデルが判断し、書いた瞬間から検索できる。古いカードが退役するのは、新しいカードと矛盾したときだけ。経過時間も容量も理由にならない。

> カード：DS のボタンは Safari で appearance: none が要る。ないと角丸が失われる。

**変数。** ホスト別のモデル階級表、プロジェクトのデザインシステムの所在、あなた自身が定義するキーと値。これらは AGENTS.md に描き出される。AGENTS.md に「実装は主力階級で」と書けば、Claude Code と Codex がそれぞれ自分のモデルに読み替える。

## モデルの前にどう現れるか

プロンプトが送られる前に、ホストがそれをエンジンに渡して一度検索する。強く関係するものがあれば、見出しをコンテキストに送る。

```
[Story 完了] ログインボタンを DS コンポーネントへ · 受け入れ：三状態が Storybook と一致
[議事録 D3] 旧ボタンスタイルは 1.4 まで残し、1.5 で削除
[カード] DS ボタンは Safari で appearance: none が必要
```

強く関係するものがなければ、何もしない。本文が要るときはモデルが自分で取りに行く。一つ仕事を終えたら、モデルは結果を作業項目に書き戻し、決定があれば議事録に、教訓があればカードに書く。

## こういうときに欲しくなる

- 作業が三日と五セッションにまたがり、四日目のモデルが初日に決めたことをまだ知っている。
- Claude Code、Codex、DeepSeek Harness を交互に使い、どれにも同じ記憶を読ませたい。
- 夜間に無人でバッチ実装を走らせ、朝に各ステップが何をどの決定に基づいてやったか辿れる。
- デスクトップが動いたまま、ノートを持って外に出て続きを書く。

いまは一人が複数デバイスで使う形を想定している。複数人で一つの記憶を共有する機能はない。

## 記憶プラグインではなく、これを選ぶ理由

世にある記憶の仕組みの多くは、ベクトルストアかメモの束だ。会話の断片を保存し、似たものを引き上げる。覚えているのは「何を言ったか」。Einzbern が覚えるのは「何を決めたか、何をするか、何を学んだか」で、三種の記録はそれぞれ構造を持ち、番号で互いを参照する。

| 必要なもの | 記憶プラグイン | Einzbern |
|---|---|---|
| ある決定とその経緯 | 似た会話の断片 | 番号付きの議事録。作業項目とカードが番号で指す |
| ある仕事がどこまで進んだか | なし | 作業項目は四階層。関係はフィールド：何が何を塞ぐか、何が何に取って代わるか、どの議事録が決めたか |
| ホストの切り替え | それぞれ別に記憶 | Claude Code、Codex、DeepSeek Harness が同じ Ether を読む |
| デバイスの切り替え | 手動同期か、同期なし | クラウドフォルダに置く。デバイスごとに一つのストリーム、同時書き込みでも衝突しない |
| 見る、変える | ファイルを開く | Atelier：変数、ルール、ゲート設定、保管庫の状態を一枚のページで管理。変更は即座に AGENTS.md へ描き出される |
| モデルの仕事の仕方 | プラグインは関知しない | 縛らない。七つの原則は既定で無効、プロジェクトごとに選ぶ |
| 記録は改竄できるか | できる | 追記のみのハッシュチェーン。一つ変えれば以降がすべて合わなくなる |

変数はプラグインとの違いのもう半分だ。ホスト別のモデル階級表、デザインシステムの所在、あなた自身のキーと値。すべて Atelier で編集し、AGENTS.md に描き出され、同じルール文が各ホストでそれぞれのモデルに読み替えられる。

## インストール

Einzbern は一つのスキルと一緒にやって来る。Mana Orchestrate（マナ・オーケストレート）。Mana は巡る記憶、Orchestrate はそれをいつどこへ流すかの指揮。このスキルはモデルにエンジンのどの機能をいつ呼ぶかを教え、インストールウィザードも同梱する。

skills コマンドで入れる。

```
npx skills add tpmoonchefryan/mana-orchestrate
```

あるいはホストに言う。Mana Orchestrate というスキルを探して入れて。

次にプロジェクトのディレクトリで言う。Einzbern をインストールして。ウィザードは一画面で質問する。新規か既存の `Ether` からの復元か、生成物をどこに置くか、そこがクラウド同期フォルダか、言語は何か、AGENTS.md にナビゲーション節を書くか。最後に書き込む予定のファイルを全部列挙し、あなたが一度だけ確認する。更新、修復、旧版からの移行、アンインストール、健全性チェックは同じウィザードのモードだ。

コミットもプッシュもしない。あなたの .gitignore を書き換えず、何も削除せず、エンジンのダウンロード以外でネットワークに触れない。

## 日々の使い方

あなたは普段どおり仕事をする。記憶は勝手に現れる。

見たいとき、変えたいときは Atelier（アトリエ）を開く。魔術師の工房。ここでは、あなたのマシン上の一枚のウェブページだ。どの原則が有効か、変数は何か、ゲートはどう設定されているか、記憶の保管庫はいまどういう状態か。常駐しない。必要なときに開く。

AGENTS.md はあなたのものだ。Einzbern が書くのは印の付いた節だけ。あなたが有効にした原則と、モデルに描き出す変数。節をあなたが書き換えたら、以後は上書きしない。どう扱うかは Atelier であなたが選ぶ。

内蔵の原則は七つで、Command Spell（令呪）と呼ぶ。サーヴァントが拒めない命令。ただし強制ではない。既定ではすべて無効で、Atelier でプロジェクトごとに自分で選んで有効にする。有効にしなくても記憶そのものは変わらず動く。

- 自律運転：作業の途中で「続けますか」と聞かない。可逆な操作はそのまま行い、破壊的な操作と範囲の変更だけで止まる。
- バッチ処理：一度の分解で生まれた作業項目が一つのバッチ。赤は記録するだけでその場で直さず、バッチの終わりに一度で処理し、報告もバッチに一度。
- 無人運転時のコマンド：確認ダイアログを出す書き方を使わない。削除は移動に置き換え、コマンド内で cd せず、作業ディレクトリの中だけに書く。
- 沈黙報告：作業中は報告を出さない。すべて完了したか、残りがすべて塞がったときにだけ報告する。
- デザインの正本と一貫性：まずプロジェクトのデザインの正本と公開済みのコンポーネント仕様を読む。コンポーネントと見た目の変更は先に正本を直し、公開されてから取り込み、同じ種類のコンポーネントは一貫させる。
- 無効な残余の後始末：一時ディレクトリ、複製、ワークツリー、バックグラウンドプロセスは作った者が責任を持つ。バッチが終わったら（失敗でも）用途に応じて片付け、証拠と作り直せる複製は分けておく。
- 目標記述契約：goal には検証できる終状態だけを書き、許可は書かない。どの goal にも「あなたにしかできない決定で塞がっている」という出口を付ける。

## 複数デバイスとクラウドフォルダ

`Ether` は共有ライブラリのフォルダー名で、親ディレクトリはユーザーが選びます。ローカルディスク、外付けディスク、OneDrive や iCloud などの同期フォルダーを利用できます。複数のプロジェクトを一つのライブラリ内で識別し、後から追加するプロジェクトも選んだ場所を既定で再利用します。イベントは `akasha/<デバイスid>/`、キャッシュ・書き込みロック・バックアップはデバイスごとに `Ether/.einzbern/<デバイスid>/` に保存します。デバイスID、登録情報、ホスト設定、インストール済みエンジンはローカルの `~/.einzbern/` に残ります。既存の `.ether` ライブラリにも対応します。

## 私たち自身の使い方

これは Einzbern 自身の開発の進め方であり、私たちが薦める使い方でもある。どれか一層だけ採ってもよい。

**二つの対話。** 一つは設計の対話。旗艦階級で、あなたと方向を議論し、決定を議事録に残し、やることを Initiative、Epic、Story に分けて Ether に書く。もう一つは実装の対話。主力階級で、Ether から Story を読み、コードは書かず、派遣、記録、ゲート、報告だけを行う。

**一括で終える。** 実装の対話は経済階級のサブエージェントを一つ派遣し、Initiative の全 Story を一度に Subtask へ分解させる。各 Subtask には変更するファイルと依存を書く。次に依存とファイルの重なりでパッケージに分ける。関係のあるものは同じパッケージで順に、無関係なものはそれぞれ別のパッケージに。パッケージごとに経済階級のサブエージェントを一つ、自分の git worktree で並行して作業させ、終われば退役。全部終わったら統合サブエージェントが依存順に合流し、バッチの終わりにゲートを一度、受け入れを一度、欠陥は一括で手直しする。

**当時の四つの原則はすべて有効。** 自律運転：可逆な操作はそのまま行う。バッチ処理：赤は記録するだけで、バッチの終わりに一度で処理する。無人運転時のコマンド：確認ダイアログを出す書き方を使わない。沈黙報告：すべて完了したか、残りがすべて塞がったときにだけ報告する。

**あなたが現れるのは二つの時点だけ。** 設計の対話で決めるとき。実装の対話がバッチを締めたときの報告を読むとき。報告にはあなたの判断を待つ事項が一度に並び、それぞれに推奨が付く。

### サブスクリプションとモデル階級（2026-09-26 時点）

薦めるサブスクリプションは Claude Max 5x か ChatGPT Pro 5x。並行サブエージェントの上限はサブスクリプションに合わせる。目安より上げると週の上限がすぐ減る。上限は Atelier の execution.maxConcurrentSubagents で変える。

| サブスクリプション | 並行サブエージェントの上限 |
|---|---|
| Claude Pro または ChatGPT Plus | 1 か 2 |
| Claude Max 5x または ChatGPT Pro 5x | 3 |
| 20x のプラン | 8 以上 |

並行は多いほどよいわけではない。上限が尽きかけたら自動で縮める。いつ縮めるかは四つのシステム変数で決まり、すべて Atelier で変える。

| 変数 | 既定 | 意味 |
|---|---|---|
| quota.fiveHourParallelOffPercent | 75 | 5 時間の上限をこの割合まで使ったら、並行サブエージェントの上限を 1 に下げる |
| quota.fiveHourWaitPercent | 90 | 5 時間の上限をこの割合まで使ったら、サブエージェントを派遣せずウィンドウのリセットを待つ |
| quota.weeklyParallelOffPercent | 95 | 週の上限をこの割合まで使ったら、並行サブエージェントの上限を 1 に下げる |
| quota.weeklyWaitPercent | 未設定 | 週の上限には待機のしきい値を置かない。設定したときだけ効く |

下の階級表は私たちがいま使っているもので、モデル名はベンダーの更新で古くなる。Atelier で管理する models.tiers を正とすること。

| ホスト | 旗艦階級 | 主力階級 | 経済階級 |
|---|---|---|---|
| Claude Code | claude-fable-5-1、max、設計の対話のみ、派遣しない | claude-opus-5-5、max、サブエージェントの編成と受け入れ | claude-opus-5-5、low、分解とパッケージ実装 |
| Codex | gpt-6-astra、max | gpt-6-sol、max | gpt-6-luna、max |

## 内蔵の原則がトークンを無駄にしない仕組み

当時の四つの原則は規律であるだけでなく、それぞれが実測した無駄を一つずつ塞いでいる。数字は Einzbern 自身の開発記録から。2026-09-26、同じ作業、同じモデル。

| どこで漏れるか | 実測 | 塞ぐ原則 |
|---|---|---|
| 一つのサブエージェントが走り続け、コンテキストが膨らみ、毎ターン全部を読み直す | 一つのサブエージェントで 30 の Subtask：平均コンテキスト 526k、3,740 ターン、加重 221M トークン、一枚あたり 7.4M | バッチ処理：パッケージを並行し、パッケージごとに新しいサブエージェントを一つ、終われば退役。新しいパッケージ用サブエージェントは一枚 2.9M、その 39% |
| 赤が出た端から直し、直したらまた赤、ゲートを何度も回す | 前の版では 9 件の欠陥票が一つの予算ゲートの周りを回り、一つのフックの欠陥に 4 回のコミット | バッチ処理：赤は記録するだけでその場で直さず、バッチの終わりに一度で処理し、同じ根本原因は一件と数える |
| 上限ウィンドウの終わり際に一波を派遣し、全部が無駄になる | 8 つの並行サブエージェントが 12 分で 5 時間の上限を使い切り、コミットゼロ、約 15M が無駄 | 上限のゲート：派遣前に残量を読む。75% で並行を落とし、90% でリセットを待つ |
| 確認ダイアログが出て、セッションが人を待ち続ける | 一度の待ちが 2 時間 12 分 | 無人運転時のコマンド：ダイアログを出す書き方を使わない |
| 主対話が派遣のたびに報告を書く | 一段で数千トークン。すべて主対話のコンテキストに残り、以後毎ターン読み直される | 沈黙報告：すべて完了か、すべて塞がったときにだけ報告する |
| 途中で「続けますか」と聞いて返事を待つ | 誰もいなければ一晩待つ | 自律運転：可逆な操作はそのまま行う |

コストの八九割はキャッシュ読み取り、つまり毎ターンのコンテキスト再読だ。サブエージェント起動時に注入されるシステムプロンプトとルールは 52k で、サブエージェント一つのコストの 1% 未満。だからトークンを節約する鍵は注入を減らすことではなく、各サブエージェントのコンテキストを短く、ターンを少なくすることにある。分解ファイル全体ではなくパッケージごとの抜粋ファイル、コマンド出力はファイルに落として末尾だけ読む、大きなファイルは範囲指定で読む、隣り合うコマンドは一つにまとめる。これらはバッチ処理の原則と実装の対話の起動ファイルに書いてある。

並行そのものはトークンを節約しない。使う速さが変わるだけだ。節約するのは新しいコンテキストだ。だから並行の上限はサブスクリプションに合わせ、残量が尽きかけたら上限のゲートが自動で縮める。

## なぜこの設計か

**記憶を提供する。やり方は縛らない。** 前の版はゲート、証明、Stop フックでモデルを囲い込もうとした。百を超える動詞、十六のゲート。自分たちで二か月使った。コストは利益を大きく上回り、忘れるものはやはり忘れた。この版はそれらを取り去り、記録と検索だけを残した。

**フックは一本だけ。** モデルは自分が知らないことを知らない。だから検索はモデルが思い出すのを待たず、ホストが毎回のプロンプトの前に起動する。ただしフックにはルールを一切入れない。何を取り、どれだけ渡すかはエンジンが決める。

**AGENTS.md はあなたのファイル。** 二つのホストで同時に効くルールは、両方が読む場所にしか書けない。だから Einzbern はそこに書くが、印の付いた節だけ、あなたが有効にしたものだけ、そしてあなたの編集には触れない。

**索引するのは Story だけ。** Initiative と Epic は粗すぎ、Subtask は細かすぎる。知りたいことは Story を見れば分かる。

**記録は追記のみ。** 派生状態はすべて記録から再構築できる。索引をローカルに置けるのも、デバイス同士を統合できるのも、この一点による。

**設定は二層。** プロジェクト設定は記録と一緒に同期し、デバイス設定はマシンに残る。新しいデバイスで設定し直すのはデバイスであって、プロジェクトではない。
