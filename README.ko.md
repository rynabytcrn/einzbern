## 수요일 오후에 일어난 일

월요일, 당신은 Claude Code에서 한 가지를 정했다. 로그인 페이지의 버튼을 디자인 시스템의 새 컴포넌트로 바꾸고, 옛 스타일은 1.4까지 남긴다.

수요일, 당신은 Codex에서 "가입 페이지도 겸사겸사 바꿔 줘"라고 말한다. 손을 대기 전에, 컨텍스트에는 이미 세 줄이 들어 있다. 월요일의 그 Story와 인수 기준, "옛 스타일은 1.4까지 남긴다"는 결정, 그리고 지난주에 남긴 카드 하나: 이 컴포넌트는 Safari에서 속성을 하나 더 붙여야 한다.

당신은 아무것도 붙여 넣지 않았고, 찾아보라고 일러 주지도 않았다. Einzbern이 하는 일은 이것이 전부다. 적어 두고, 필요한 순간에 꺼낸다.

## 소원 기계

성배는 소원 기계다. 빌면, 결과가 온다. 소원 기계에는 공통점이 하나 있다. 소원이 구체적이지 않으면, 이루어진 것은 당신이 원한 것이 아닐 가능성이 높다.

Einzbern은 이를 따른다. 강제하는 것은 딱 두 가지다. 작업 항목에는 목표를 적을 것, 무엇을 완료로 볼지 적을 것. 어떻게 쓰고, 어떻게 나누고, 어떻게 진행할지는 모델이 자기 생각대로 한다. Einzbern은 끼어들지 않는다.

작업 항목, 지식, 회의록과 변수는 사용자가 선택한 위치의 공유 라이브러리 `Ether`에 저장된다. 여러 프로젝트는 그 안에서 구분된다. 모델은 프롬프트 전에 읽고 작업을 마치면 기록한다.

## 무엇을 기억하나

**소원: 작업 항목.** Initiative, Epic, Story, Subtask 네 단계. Story는 가장 작은 완결된 의도이며, 색인하는 것은 Story뿐이다. 작업 항목 사이의 관계는 필드이지 문장이 아니다. 무엇이 무엇을 막는지, 무엇이 무엇을 구현하는지, 무엇이 무엇을 대체하는지, 어느 회의록이 결정했는지.

> Story: 로그인 버튼을 DS 컴포넌트로 교체. 인수: 기본, 호버, 비활성 세 상태가 Storybook과 일치.

**결정: 회의록.** 당신의 결정과, 모델이 내린 기술적 결정. 모든 결정에는 번호가 있고, 작업 항목과 카드는 번호로 인용한다. 모델에게 회의를 요구하지 않는다. 적어 두기만을 요구한다.

> 회의록 D3: 옛 버튼 스타일은 1.4까지 유지, 1.5에서 제거.

**함정: 지식.** 카드 한 장에 환경에 관한 사실 하나 또는 교훈 하나. 어떤 작업 항목이나 회의록도 필드로 담지 않는 종류의 것. 무엇이 남길 가치가 있는지는 모델이 판단하고, 쓰는 순간부터 검색된다. 옛 카드는 새 카드와 충돌할 때만 퇴역한다. 시간도 이유가 아니고, 용량도 이유가 아니다.

> 카드: DS 버튼은 Safari에서 appearance: none이 필요하다. 없으면 둥근 모서리가 사라진다.

**변수.** 호스트별 모델 등급표, 프로젝트의 디자인 시스템 주소, 당신이 직접 정의한 키와 값. 이것들은 AGENTS.md에 렌더링된다. AGENTS.md에 "구현은 주력 등급으로"라고 쓰면, Claude Code와 Codex가 각자 자기 모델로 환산한다.

## 모델 앞에 어떻게 나타나나

프롬프트가 전송되기 전에, 호스트가 그것을 엔진에 넘겨 한 번 검색한다. 강하게 관련된 것이 있으면 제목을 컨텍스트에 넣는다.

```
[Story 완료] 로그인 버튼을 DS 컴포넌트로 교체 · 인수: 세 상태가 Storybook과 일치
[회의록 D3] 옛 버튼 스타일은 1.4까지 유지, 1.5에서 제거
[카드] DS 버튼은 Safari에서 appearance: none 필요
```

강하게 관련된 것이 없으면 아무것도 하지 않는다. 본문이 필요하면 모델이 직접 가져온다. 일을 하나 마치면 모델은 결과를 작업 항목에 적어 넣고, 결정이 있으면 회의록에, 교훈이 있으면 카드에 쓴다.

## 이럴 때 필요해진다

- 작업이 사흘 다섯 세션에 걸치는데, 나흘째의 모델이 첫날 정한 것을 여전히 알고 있다.
- Claude Code, Codex, DeepSeek Harness를 번갈아 쓰며 모두가 같은 기억을 읽기를 바란다.
- 밤새 무인 배치 구현을 돌리고, 아침에 각 단계가 무엇을 어느 결정에 따라 했는지 되짚을 수 있다.
- 데스크톱은 돌아가는 채로, 노트북을 들고 나가 이어서 쓴다.

지금은 한 사람이 여러 기기에서 쓰는 형태를 상정한다. 여러 사람이 하나의 기억을 공유하는 기능은 없다.

## 기억 플러그인이 아니라 이것을 고르는 이유

세상의 기억 방식 대부분은 벡터 저장소이거나 메모 더미다. 대화 조각을 저장했다가 비슷한 것을 건져 올린다. 기억하는 것은 "무엇을 말했는가". Einzbern이 기억하는 것은 "무엇을 결정했고, 무엇을 할 것이며, 무엇을 배웠는가"이고, 세 종류의 기록은 각자 구조를 가지며 번호로 서로를 가리킨다.

| 필요한 것 | 기억 플러그인 | Einzbern |
|---|---|---|
| 어떤 결정과 그 경위 | 비슷한 대화 조각 | 번호가 붙은 회의록. 작업 항목과 카드가 번호로 가리킨다 |
| 어떤 일이 어디까지 됐는지 | 없음 | 작업 항목 네 단계. 관계는 필드: 무엇이 무엇을 막는지, 무엇이 무엇을 대체하는지, 어느 회의록이 결정했는지 |
| 호스트 바꾸기 | 각자 따로 기억 | Claude Code, Codex, DeepSeek Harness가 같은 Ether를 읽는다 |
| 기기 바꾸기 | 수동 동기화 또는 동기화 없음 | 클라우드 폴더에 둔다. 기기마다 스트림 하나, 동시에 써도 충돌 없음 |
| 보고, 바꾸기 | 파일 열기 | Atelier: 변수, 규칙, 게이트 설정, 저장소 상태를 한 페이지에서 관리. 바꾸면 곧바로 AGENTS.md에 렌더링 |
| 모델이 일하는 방식 | 플러그인은 관여하지 않음 | 묶지 않는다. 일곱 가지 원칙은 기본 꺼짐, 프로젝트별로 선택 |
| 기록을 고칠 수 있는가 | 있다 | 추가만 하는 해시 체인. 하나를 바꾸면 그 뒤가 전부 맞지 않는다 |

변수는 플러그인과 다른 나머지 절반이다. 호스트별 모델 등급표, 디자인 시스템 주소, 당신 자신의 키와 값. 모두 Atelier에서 고치고 AGENTS.md에 렌더링되어, 같은 규칙 문장이 각 호스트에서 자기 모델로 환산된다.

## 설치

Einzbern은 스킬 하나와 함께 온다. Mana Orchestrate(마나 오케스트레이트). Mana는 흐르는 기억, Orchestrate는 그것을 언제 어디로 흘려보낼지 지휘하는 일. 이 스킬은 모델에게 엔진의 어느 기능을 언제 부를지 가르치고, 설치 마법사도 함께 담고 있다.

skills 명령으로 설치한다.

```
npx skills add tpmoonchefryan/mana-orchestrate
```

또는 호스트에게 말한다. Mana Orchestrate라는 스킬을 찾아서 설치해 줘.

그다음 프로젝트 디렉터리에서 말한다. Einzbern을 설치해 줘. 마법사는 한 화면으로 질문한다. 새로 설치할지 기존 `Ether`에서 복원할지, 산출물을 어디에 둘지, 그곳이 클라우드 동기화 폴더인지, 언어는 무엇인지, AGENTS.md에 내비게이션 절을 쓸지. 마지막으로 기록할 파일을 전부 나열하고, 당신이 한 번만 확인한다. 업데이트, 복구, 이전 버전에서의 이전, 제거, 상태 점검은 같은 마법사의 모드다.

커밋도 푸시도 하지 않는다. 당신의 .gitignore를 고치지 않고, 아무것도 지우지 않으며, 엔진 다운로드 외에는 네트워크에 접속하지 않는다.

## 평소 쓰는 법

당신은 평소처럼 일한다. 기억은 알아서 나타난다.

보고 싶거나 바꾸고 싶을 때는 Atelier(아틀리에)를 연다. 마술사의 공방. 여기서는 당신 컴퓨터의 웹 페이지 하나다. 어떤 원칙이 켜져 있는지, 변수는 무엇인지, 게이트는 어떻게 설정되어 있는지, 기억 저장소는 지금 어떤 상태인지. 상주하지 않는다. 필요할 때 연다.

AGENTS.md는 당신의 것이다. Einzbern은 표시가 붙은 절만 쓴다. 당신이 켠 원칙과, 모델에게 렌더링할 변수. 절을 당신이 고치면 더는 덮어쓰지 않고, 어떻게 처리할지는 Atelier에서 당신이 고른다.

내장 원칙은 일곱 가지이며 Command Spell(영주)이라 부른다. 서번트가 거부할 수 없는 명령. 다만 강제는 아니다. 기본값은 모두 꺼짐이고, Atelier에서 프로젝트별로 직접 골라 켠다. 켜지 않아도 기억 자체는 그대로 동작한다.

- 자율 운전: 작업 도중 "계속할까요"라고 묻지 않는다. 되돌릴 수 있는 동작은 그냥 하고, 파괴적 동작과 범위 변경에서만 멈춘다.
- 배치 처리: 한 번의 분해로 나온 작업 항목이 한 배치. 빨간불은 기록만 하고 그 자리에서 고치지 않으며, 배치 끝에 한 번에 처리하고, 보고도 배치당 한 번.
- 무인 운전 명령: 확인 대화상자를 띄우는 작성법을 쓰지 않는다. 삭제는 이동으로 바꾸고, 명령 안에서 cd 하지 않으며, 작업 디렉터리 안에만 쓴다.
- 침묵 보고: 작업 중에는 보고를 내지 않는다. 전부 끝났거나 남은 것이 전부 막혔을 때만 보고한다.
- 디자인 기준 및 일관성: 먼저 프로젝트의 디자인 기준과 공개된 컴포넌트 규격을 읽는다. 컴포넌트와 시각 변경은 기준부터 고치고 공개된 뒤에 받아들이며, 같은 종류의 컴포넌트는 일관되게 유지한다.
- 무효 잔여물 정리: 임시 디렉터리, 복사본, 워크트리, 백그라운드 프로세스는 만든 쪽이 책임진다. 배치가 끝나면(실패해도) 용도에 따라 정리하고, 증거와 다시 만들 수 있는 복사본은 따로 둔다.
- 목표 작성 계약: goal에는 검증할 수 있는 최종 상태만 쓰고 허가는 쓰지 않는다. 모든 goal에 "당신만 내릴 수 있는 결정에 막혀 있다"는 출구를 붙인다.

## 여러 기기와 클라우드 폴더

`Ether`는 공유 라이브러리 폴더의 이름이며 상위 경로는 사용자가 선택합니다. 로컬 디스크, 외장 디스크 또는 OneDrive와 iCloud 같은 동기화 폴더에 둘 수 있습니다. 여러 프로젝트는 하나의 라이브러리 안에서 식별되며 이후 프로젝트도 선택한 위치를 기본으로 재사용합니다. 이벤트는 `akasha/<기기id>/`에, 캐시·쓰기 잠금·백업은 기기별 `Ether/.einzbern/<기기id>/`에 저장됩니다. 기기 ID, 등록 정보, 호스트 설정과 설치된 엔진은 로컬 `~/.einzbern/`에 남습니다. 기존 `.ether` 라이브러리도 계속 지원합니다.

## 우리는 이렇게 쓴다

이것은 Einzbern 자신을 개발하는 방식이자 우리가 권하는 사용법이다. 한 층만 가져다 써도 된다.

**대화 둘.** 하나는 설계 대화. 플래그십 등급으로 당신과 방향을 논의하고, 결정을 회의록으로 남기고, 할 일을 Initiative, Epic, Story로 나눠 Ether에 쓴다. 다른 하나는 구현 대화. 주력 등급으로 Ether에서 Story를 읽고, 코드는 쓰지 않으며, 파견, 기록, 게이트, 보고만 한다.

**한 배치로 끝낸다.** 구현 대화는 경제 등급 서브에이전트 하나를 보내 Initiative의 모든 Story를 한 번에 Subtask로 나누게 한다. 각 Subtask에는 바꾸는 파일과 의존을 적는다. 그다음 의존과 파일 겹침으로 패키지를 나눈다. 관련 있는 것은 같은 패키지에서 순서대로, 무관한 것은 각자 패키지로. 패키지마다 경제 등급 서브에이전트 하나가 자기 git worktree에서 병렬로 일하고, 끝나면 퇴역한다. 전부 끝나면 통합 서브에이전트가 의존 순서로 합치고, 배치 끝에 게이트 한 번, 인수 한 번, 결함은 한 배치로 재작업한다.

**당시의 네 원칙을 모두 켠다.** 자율 운전: 되돌릴 수 있는 동작은 그냥 한다. 배치 처리: 빨간불은 기록만 하고 배치 끝에 한 번에 처리한다. 무인 운전 명령: 확인 대화상자를 띄우는 작성법을 쓰지 않는다. 침묵 보고: 전부 끝났거나 남은 것이 전부 막혔을 때만 보고한다.

**당신이 나타나는 순간은 둘뿐.** 설계 대화에서 결정할 때. 구현 대화가 배치를 닫으며 낸 보고 하나를 읽을 때. 보고에는 당신의 결정을 기다리는 항목이 한 번에 나열되고 각각에 권고가 붙는다.

### 구독과 모델 등급 (2026-09-26 기준)

권하는 구독은 Claude Max 5x 또는 ChatGPT Pro 5x. 병렬 서브에이전트 상한은 구독에 맞춘다. 권장값보다 올리면 주간 한도가 너무 빨리 준다. 상한은 Atelier의 execution.maxConcurrentSubagents에서 바꾼다.

| 구독 | 병렬 서브에이전트 상한 |
|---|---|
| Claude Pro 또는 ChatGPT Plus | 1 또는 2 |
| Claude Max 5x 또는 ChatGPT Pro 5x | 3 |
| 20x 플랜 | 8 이상 |

병렬이 많을수록 좋은 것은 아니다. 한도가 바닥날 때는 스스로 줄어야 한다. 언제 줄일지는 시스템 변수 넷이 정하며, 모두 Atelier에서 바꾼다.

| 변수 | 기본값 | 의미 |
|---|---|---|
| quota.fiveHourParallelOffPercent | 75 | 5시간 한도를 이 비율까지 쓰면 병렬 서브에이전트 상한을 1로 낮춘다 |
| quota.fiveHourWaitPercent | 90 | 5시간 한도를 이 비율까지 쓰면 서브에이전트를 더 보내지 않고 창이 초기화되기를 기다린다 |
| quota.weeklyParallelOffPercent | 95 | 주간 한도를 이 비율까지 쓰면 병렬 서브에이전트 상한을 1로 낮춘다 |
| quota.weeklyWaitPercent | 미설정 | 주간 한도에는 대기 임계값을 두지 않는다. 설정해야만 적용된다 |

아래 표는 모델 설정의 예시이며 기본값이나 워크플로의 고정 구성이 아닙니다. 실제 모델과 추론 강도는 Atelier에서 관리하는 models.tiers를 따릅니다.

| 호스트 | 플래그십 | 주력 | 경제 |
|---|---|---|---|
| Claude Code | claude-fable-5-1, max, 설계 대화 전용, 파견하지 않음 | claude-opus-5-5, max, 서브에이전트 편성과 인수 | claude-opus-5-5, low, 분해와 패키지 구현 |
| Codex | gpt-6-astra, max | gpt-6-sol, max | gpt-6-luna, max |

## 사용량을 줄이는 방법

> **Codex 전용 워크플로를 사용할 수 있습니다.** Codex Desktop은 주력 등급의 의사결정 대화와 경제 등급의 조정 대화를 독립적으로 운영합니다. 다른 호스트는 각자의 네이티브 경로를 유지합니다. 아래 비용은 2026-10-31에 과거 표본으로 계산한 값이며, 명시한 추정 조건에 따른 비교입니다. 일정한 사용 한도 절감을 보장하지 않습니다.

장시간 작업의 소모는 코드 작성에서만 생기지 않습니다. 파견, 대기 후 재개, 상태 복구, 로그 읽기, 서브에이전트 결과 수신도 모델이 컨텍스트를 반복 처리하게 할 수 있습니다. Einzbern과 Mana Orchestrate는 작업 분담, 배치 경계, 컨텍스트 범위를 통해 이런 비용을 관리합니다.

- **작업에 맞는 모델 범주를 선택합니다.** 계획, 복잡한 판단, 독립 인수 검증은 주력 범주에서 시작하고, 범위가 명확한 실행과 일상적인 조정에는 설정된 경제 범주를 사용합니다. 실제 모델과 추론 강도는 호스트 정책이 결정하며 특정 모델에 고정하지 않습니다.
- **배치 전체 목표를 실행합니다.** 분해 후 의존 관계에 따라 패키지를 나눕니다. 작업 에이전트가 맡은 일을 끝내면 배치 말에 인수 검증과 문제 처리를 모아 수행하여 항목별 완료, 파견, 검증에 따르는 반복 왕복을 줄입니다.
- **필요한 내용만 읽습니다.** 문제와 증거는 배치 기록에 남깁니다. 주 대화는 결정에 필요한 결과와 증거 위치를 받고, 큰 파일·로그·계획은 발췌해 읽습니다.
- **모든 역할을 비용에 포함합니다.** 주 대화, 경제 조정 대화, 작업 에이전트를 함께 집계하고 실패, 재시도, 결과 전달 비용도 포함합니다. 주 대화 사용량 감소는 전체 흐름의 사용량과 함께 판단해야 합니다.

### 호스트마다 다른 조정 방식을 사용합니다

| 호스트 | 적용 방식 | 최적화 초점과 근거 |
| :--- | :--- | :--- |
| **Codex Desktop: 전용 두 대화 방식** | 독립된 주력 의사결정 대화가 배치 전체 목표를 넘깁니다. 독립된 경제 조정 대화가 작업 서브에이전트를 파견하고 기다리며 결과를 받은 뒤, 배치 말에 주력에 한 번 보고합니다. | 과거 실행에서는 빈번한 조정을 긴 주력 대화에 남기면 비용 영향이 컸습니다. 이를 경제 범주에 맡겨 주력 대화의 호출 빈도를 관리합니다. |
| **Claude Code: 네이티브 경로 유지** | 하나의 주 대화가 호스트의 백그라운드 실행과 완료 알림을 사용해 작업 서브에이전트를 조정합니다. | 네이티브 알림으로 결과를 받을 수 있습니다. 모델 범주, 예약된 깨우기, 반환 내용, 검증 주기를 계속 최적화합니다. 현재 표본은 별도 조정 대화가 일반적으로 필요하다는 점을 입증하지 않습니다. |
| **DeepSeek Harness: 네이티브 경로 유지** | 하나의 주 대화가 런타임 관리 서브에이전트를 사용하고, Mana Orchestrate 플러그인이 기억 연결과 브리지 중복 제거를 담당합니다. | 런타임이 완료 알림과 리소스 회수를 담당합니다. 과거 기록에서도 여러 반환이 하나의 주 대화 응답으로 합쳐지는 사례가 관찰됐습니다. 실제 모델과 조정 비용 비중에 따라 추가 최적화를 평가합니다. |

두 대화 방식은 **Codex 워크플로의 유일한 방식**이며 기존 수집 hook 경로를 대체했습니다. 다른 호스트에는 영향을 주지 않습니다. 경제 조정 대화는 작업 에이전트 결과를 직접 받고 별도 수집 에이전트를 두지 않습니다. 구현, 통합, 독립 인수 검증은 해당 작업 에이전트가 담당합니다. 주력과 경제 모델 범주는 필수이며 플래그십은 선택 사항입니다.

이 편성은 모델이 호스트에서 지원하는 도구로 실행합니다. 엔진은 배치와 수신 기록을 저장하며, 스스로 대화를 만들거나 작업을 파견하거나 메시지를 보내지 않습니다.

Codex 자체도 서브에이전트, 대기, 결과 집계를 지원합니다. 전용 방식은 관찰된 조정 비용을 대상으로 합니다. CC와 DSH가 네이티브 경로를 유지한다고 해서 결과 반환 후 컨텍스트 처리가 없거나 앞으로도 최적화가 필요 없다는 뜻은 아닙니다. 호스트 기능은 [Codex 서브에이전트 문서](https://learn.chatgpt.com/docs/agent-configuration/subagents), [Claude Code 백그라운드 서브에이전트 문서](https://code.claude.com/docs/en/sub-agents#run-subagents-in-foreground-or-background), [DSH 네이티브 위임 문서](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/subagent/tool-subagent/README.md)를 참조하세요.

### Codex 사례: 29.3시간의 같은 사용량으로 추정한 세 가지 방식

한 디자인 시스템 개발 기록은 **29.3시간, 81개 대화, 고유 모델 응답 7,763개**를 포함하며 주력 의사결정, 경제 조정, 모든 작업 에이전트를 집계합니다. 표본 마감 시점에도 작업은 진행 중이었습니다. 아래 수치는 관측 시간 내 사용량이며, 최종 인수 검증을 통과한 전체 납품 비용이 아닙니다.

| 작업 방식 | Standard 참고 credits | 주력 조정 방식을 100%로 한 비율 | 데이터 성격 |
| :--- | ---: | ---: | :--- |
| **주력 의사결정 + 경제 조정 + 범주별 작업 에이전트** | **2,610.58** | **49.3%** | 관측된 요청과 사용량을 각 응답의 실제 모델 요율로 환산 |
| 주력이 모든 조정과 대기를 담당하고 작업 에이전트는 유지 | 약 5,300.52 | 100% | 요청·token·캐시 구성을 유지하고 경제 조정을 주력 모델 요율로 재계산 |
| 서브에이전트 없이 모든 작업을 주 대화에서 수행 | 약 5,116.83 | 96.5% | 식별 가능한 순수 에이전트 통신을 제외한 뒤 남은 작업을 주력 모델 요율로 재계산 |

이 추정에서 두 대화 방식의 비용은 주력 조정보다 약 **50.7%**, 주력 단독 수행보다 약 **49.0%** 낮습니다. 누적 참고 비용 중 작업 에이전트가 **80.5%**, 주력 의사결정이 **10.8%**, 경제 조정이 **8.7%**를 차지합니다.

비교에 쓰인 주력 모델은 GPT-6.1 Sol이며, 실제 기록에는 GPT-6 Luna와 소량의 GPT-6.1 Terra도 포함됩니다. 이 이름은 사례의 측정 조건이며 제품에 고정된 모델 구성이 아닙니다. 참고 요율은 [OpenAI 공식 Pricing](https://learn.chatgpt.com/docs/pricing)을 따릅니다.

**50.7%는 모든 조정 작업을 같은 사용량에서 다른 요율로 계산한 차이입니다.** 파견, 대기, 복구, 결과 회수, 보고 등을 포함합니다. “배치 반환만으로 token이 50.7% 감소했다”라고 쓸 수는 없습니다. 두 비교 방식 모두 실제로 다시 실행하지 않았으므로 컨텍스트 증가, 캐시 변화, 순차 실행 시간, 납품 품질의 차이는 아직 모릅니다.

### 서브에이전트가 반환된 뒤 주 대화는 컨텍스트를 얼마나 처리하나요?

파견·대기 도구만 집계하면 결과 수신 후 처리가 빠집니다. 따라서 반환 이벤트 다음의 첫 고유 계량 응답도 포함했습니다. 여러 반환이 하나의 응답으로 합쳐지면 한 번만 세고, 스트리밍 콘텐츠 블록을 중복 집계하지 않습니다. 이는 반환 시점 주변의 처리량이며, 알림 하나가 응답 전체 비용을 일으켰다는 증거는 아닙니다.

| 표본 / 역할 | 받은 반환 이벤트 | 첫 수신 응답 | 응답당 평균 입력, 캐시 포함 | 캐시 읽기 비중 |
| :--- | ---: | ---: | ---: | ---: |
| CC: 주 대화 4개 | 완료 알림 212개 | **207회** | 약 636k token | 96.5% |
| DSH: 공식 Pro 주 대화 | 완료 알림 112개 + 결과 전달 69개 | **120회** | 약 395k token | 99.1% |
| Codex: 주력 의사결정 대화 | 배치 말 보고 12개 | **12회** | 약 272k token | 98.2% |
| Codex: 전체 경제 조정 계층 | 최종 반환 78개 + 에이전트 메시지 9개 | **87회** | 약 165k token | 97.8% |

DSH의 완료 알림 112개만 보면 첫 수신 응답은 **61회**입니다. 기존 경로에서도 반환을 합치고 있다는 뜻입니다. 별도로 전달된 결과도 응답을 일으켜 전체는 표의 120회가 됩니다.

Codex 경제 계층은 여전히 개별 반환을 받고 주력 대화는 배치 말 보고를 받습니다. 두 계층의 요청과 비용을 모두 포함했습니다. 표의 작업, 실행 시간, 모델이 서로 다르므로 횟수나 입력량을 직접 빼서 호스트 간 절감률을 계산할 수 없습니다. 누적 입력에는 캐시를 반복해서 읽은 양도 포함됩니다.

### Codex의 두 대화 방식을 당장 CC와 DSH에 확대하지 않는 이유

호스트별 실제 이력에 반환 후 처리를 더하고 선택한 작업을 경제 모델 요율로 재계산하면 추가 검증 가치가 있는 비용 여지를 추정할 수 있습니다. CC는 **Haiku 5.5**, DSH는 공식 **Flash 4.1-1017**을 비교 대상으로 사용했습니다. 추가 모델을 실행해 작업을 다시 수행하지 않았습니다.

| 과거 표본 | 조정 확인 + 첫 수신 응답을 경제 모델 요율로 계산한 전체 비용 차이 | 반환 후 처리 구간 전체를 포함한 넓은 추정 |
| :--- | ---: | ---: |
| CC: 대화 트리 4개, Opus 5.5 → Haiku 5.5 | **약 3.8%** | **약 6.6%** |
| DSH: 공식 Pro → 공식 Flash | **최대 6.8%** | **최대 11.2%** |
| DSH: 공식 Flash 소표본 → 같은 요율의 Flash | **모델 단가 차이 0%** | **모델 단가 차이 0%** |

넓은 추정은 반환 이벤트부터 다음 새 파견, 현재 턴 종료 또는 독립적인 사용자 입력까지를 계산하며 읽기, 통합, 판단을 포함합니다. 이 작업 전부를 경제 범주로 옮길 수 있는지, 추가 조정 계층의 시작·인계·캐시·품질·유지보수 비용이 얼마나 드는지는 실측하지 않았습니다. 표의 차이는 이미 달성한 절감이 아닙니다.

CC 대화 4개의 수치는 각각 약 **2.9%, 3.0%, 2.4%, 11.1%**이며 3.8%는 가중 합계입니다. 더 최근의 DSH Claude 주 대화 표본 두 개에서 조정과 첫 수신 처리를 Flash 요율로 계산한 차이는 각각 약 **0.7%–1.4%**, **5.3%–7.8%**였습니다. 이익은 모델과 작업에 따라 달라지며 모든 프로젝트에 같은 비율을 약속할 수 없습니다.

이 표본들은 Codex에 전용 두 대화 최적화를 적용하고 CC와 DSH는 기존 네이티브 경로를 유지하면서 중복 알림, 피할 수 있는 깨우기, 반환 내용, 캐시 효과를 계속 점검하는 판단을 뒷받침합니다. 네이티브 완료 알림은 연결 기능의 근거입니다. 독립 조정 대화를 추가하려면 추가 비용과 납품 품질까지 다루는 증거가 더 필요합니다.

### 대기 자체와 대기 후 모델 호출을 따로 계량합니다

대기 도구가 차단된 시간 자체는 새로운 모델 입력을 만들지 않습니다. 시간 초과 후 모델을 다시 호출하면 컨텍스트를 다시 처리하고 출력을 생성합니다.

경제 조정 계층에는 여전히 **대기 시간 초과 뒤 계량 응답 567회**가 있었고, 약 **9,181만 입력 token**을 처리했습니다. 그중 캐시 읽기는 약 **98.9%**이며 **26.95 참고 credits**로 환산됩니다. 빈번한 재개를 경제 모델로 옮기는 비용 이점을 보여 주지만, 시간 초과 후 재개를 줄일 여지도 남아 있습니다. 빈 폴링을 모두 제거했다고 주장할 수는 없습니다.

## 왜 이렇게 설계했나

**기억을 제공하되, 방법은 묶지 않는다.** 이전 버전은 게이트, 증명, Stop 훅으로 모델을 가두려 했다. 백 개가 넘는 동사, 열여섯 개의 게이트. 우리가 직접 두 달을 썼다. 비용이 이득을 훨씬 넘었고, 잊을 것은 그래도 잊었다. 이번 버전은 그것들을 걷어내고 기록과 검색만 남겼다.

**훅은 하나뿐.** 모델은 자기가 모르는 것을 모른다. 그래서 검색은 모델이 떠올리기를 기다리지 않고, 호스트가 매 프롬프트 전에 촉발한다. 하지만 훅 안에는 규칙이 하나도 없다. 무엇을 가져오고 얼마나 줄지는 엔진이 정한다.

**AGENTS.md는 당신의 파일.** 두 호스트에서 동시에 효력을 가지려면 둘 다 읽는 곳에만 쓸 수 있다. 그래서 Einzbern은 거기에 쓰지만, 표시가 붙은 절만, 당신이 켠 것만, 그리고 당신이 고친 곳은 건드리지 않는다.

**색인은 Story만.** Initiative와 Epic은 너무 거칠고, Subtask는 너무 잘다. 알아야 할 것은 Story에서 알 수 있다.

**기록은 추가만.** 모든 파생 상태는 기록에서 다시 만들 수 있다. 색인을 로컬에만 둘 수 있는 것도, 기기끼리 합칠 수 있는 것도 이 한 가지 때문이다.

**설정은 두 층.** 프로젝트 설정은 기록과 함께 동기화되고, 기기 설정은 컴퓨터에 남는다. 새 기기를 설치할 때 다시 잡는 것은 기기이지 프로젝트가 아니다.
