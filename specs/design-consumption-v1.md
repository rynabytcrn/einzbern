# design-consumption-v1

Load only when the corresponding principle is enabled and this task needs its procedures. Existing task authorization and approved methods remain authoritative; this reference adds no agents, stages or permissions to an ordinary task.


## Design Authority and Consistency Principle v1

1. First determine whether a design authority is configured. Read the current project's and target subproject's system variable `design.authority`, together with the authority repository, production documentation, and build and deployment bindings declared in the same configuration. A design authority is optional: when a project or subproject has none, record it as unconfigured and do not block work that does not depend on a design authority. A module's identity does not itself require an independent design system. When an authority is configured, the project and target subproject must resolve their effective authority; inherited values must identify their source. When declared bindings conflict or cannot resolve, stop design work that depends on that authority, without guessing from directory placement, the parent project, or memory.
2. Inspect existing components and standards. Use a configured authority's published contract to identify component families, variants, states, layouts, and interactions before implementation. Reuse existing capabilities and include missing ones in the authority's change scope.
3. Change the authority first. When a capability requires the authority to add or change a component, visual design or standard, start with an authority PR covering implementation, standards, working examples and applicable validation. Do not create a separate design in the application and document it afterwards. Reusing capabilities already published or correcting an application deviation from that contract proceeds within existing authorization; do not invent an authority gap or an additional publication dependency.
4. Consume changes after production succeeds. The application may use the new capability only after the authority PR is merged, its declared production documentation or component library is published successfully, and its declared build and deployment service succeeds, with all evidence bound to the same source commit or artifact version. A local pass, preview deployment, or reachable page does not establish production success. Include this dependency when organizing the batch and do not consume the change before it is satisfied.
5. Keep component families consistent. Preserve the family's colors, typography, spacing, sizing, radii, borders, icons, motion, and interaction states. Added features follow existing selection, feedback, and keyboard patterns. Compare equivalent components directly to prevent a substantially different visual or interaction language; obtain explicit Owner agreement before a substantial style change. Adding a substantially divergent implementation to the authority does not establish family consistency or Owner visual acceptance. Check every added or changed component and variant: equivalent tasks use equivalent controls, with consistent meanings and expectations for selection, navigation, saving, undoing, resetting, error feedback, and keyboard interaction.
6. Consume the published contract. Use published components, tokens, or an authority-approved static consumption method, bind the actual version, and refresh generated contracts and stylesheet snapshots together. Do not copy documentation-only styles, recreate reusable components in the application, or conceal missing authority support with local overrides.
7. Reconcile existing gaps. For each concrete usage, distinguish local implementation deviations, conflicting authority standards, unpublished capabilities and unverified behavior. A group of failures does not prove the entire task only awaits publication. When an application uses a capability absent from the authority or its production release, apply the approved goal: if withdrawing the incorrect usage or replacing it with a published capability preserves required behavior and the design goal, correct it directly under clause 3. If the goal still needs the missing capability, identify consumer locations and missing evidence, complete the authority PR, production publication and build, then continue application changes dependent on that new capability. Do not drop requirements merely to bypass publication. Record machine verification and Owner visual acceptance separately.
8. Separate rules from values. Reference system variables and their authority contracts in the rule body instead of hard-coding project names, repository addresses, documentation URLs, deployment vendors, versions, or component measurements. Store actual values in project or subproject configuration; a project or subproject may have no design binding. Mark unavailable configuration capabilities or unreadable evidence as unconfigured or unverified. Use the current task's existing authorization for commits and publication.

## 设计权威与一致性原则 v1

1. 先确定是否已配置设计权威。读取当前项目及目标子项目的系统变量 `design.authority`，以及同一配置中声明的权威仓库、生产文档和构建部署绑定。设计权威是可选项：项目或子项目未配置时，明确记录为未配置，且不阻塞不依赖设计权威的工作。模块身份本身不要求独立设计系统。配置了权威时，项目和目标子项目应解析各自的有效权威；继承值须显示来源。已声明绑定冲突或无法解析时，停止依赖该权威的设计工作，不按目录位置、顶层项目或记忆猜测。
2. 先查已有组件与规范。根据已配置权威的已发布契约，核对组件家族、变体、状态、布局和交互规范，再决定如何实现。已有能力直接复用；缺少能力记入设计权威的改动范围。
3. 设计权威先改。需要权威新增或改变组件、视觉设计或规范能力时，先向权威仓库提 PR，补齐实现、设计规范、实际示例和适用验证；不得先在应用中另造一套再补规范。应用按已发布契约复用现有能力、纠正自身偏离时，在原授权范围内直接修正，不虚构权威缺口或额外发布依赖。
4. 发布通过后再接入。权威 PR 合并、声明的生产文档或组件库发布成功、声明的构建部署服务成功，并核对这些证据对应同一提交或产物版本后，应用才能接入新能力。本地通过、预览部署或只有页面能打开，都不代表生产发布通过。这个发布依赖应在批次分包时明确，未满足时不越过依赖。
5. 保持组件家族一致。新增和修改的组件沿用原家族的颜色、字体、间距、尺寸、圆角、边框、图标、动效及交互状态；增量功能沿用已有选用方式、反馈和键盘操作。用同类组件逐项对照，避免产生明显不同的视觉或交互语言；较大的风格变化先取得 Owner 明确同意。把明显偏离原家族的实现补进设计权威，不能作为风格一致或 Owner 目视通过的证明。检查全部新增或修改的组件与变体：同类任务应使用同类控件，保持选择、导航、保存、撤销、重置、错误反馈和键盘操作的含义与预期一致。
6. 通过正式契约消费。应用使用已发布组件、令牌或权威认可的静态消费方式，绑定实际版本并同步生成的契约与样式快照；不复制文档站私有样式、不在应用内重造通用组件、不用局部覆盖掩盖权威缺口。
7. 核对现存缺口。按具体使用场景分别判断本地实现偏离、权威标准矛盾、未发布能力和未验证行为，不由一组失败推断整个任务只剩发布。应用使用了权威未提供或未发布的能力时，先依据已批准目标判断：能在不减少既定需求、不改变设计目标的前提下撤回错误用法或替换为已发布能力的，按第 3 条直接纠偏；目标仍需要该缺失能力时，列出使用处和缺少的权威证据，先完成权威 PR、生产发布和构建，再继续依赖该新能力的应用改动。不能为了绕过发布前置而自行删减需求。机器验证与 Owner 目视验收分别记录。
8. 规则与变量分离。规则正文只引用系统变量及其权威契约，不写死项目名、仓库地址、文档 URL、部署厂商、版本号或组件数值。当前项目使用的具体值属于项目或子项目配置；项目或子项目可以没有设计绑定。配置能力尚未实现或证据无法读取时，明确记录为未配置或未验证。提交和发布动作使用当前任务已经获得的授权。
